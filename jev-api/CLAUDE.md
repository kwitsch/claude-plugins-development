# jev-api

Mods-only plugin: a function-hooks module that registers the System One question types `noul`, `choice`, `score` as tools (`mcp__jev-api__<type>`), plus `batch` (`state` and a `questions` array of `{ type, instructions, criteria }`, one request, answers as a JSON array in question order, all or nothing), and answers them. jevfort asks Jev only through `batch`: renaming it or changing its input or answer shape breaks jevfort.

- Source layout (`src/hooks/*.mts`, built to `plugin/hooks/*.mjs`; only `register.mjs` is in `hooks.json` and stays readable (unminified, unmangled: Claude Code's static check reads it); `package.json` `pluginBuild.bundleHooksLib` makes `development/scripts/build-plugin.mts` bundle every other `hooks/*.mts` into one `plugin/hooks/lib.mjs` (compressed, whitespace removed, not mangled so `$` stays spelled) and point the entry's imports at it, so sources import each other as `./x.mjs`, top-level names stay unique across files and no module keeps state at module level, since the test kit reloads only `register.mjs` per test): `register.mts` (`register(on, options)`, the two hooks), `types.mts` (engine, hook and question types, tool and overflow name lists), `util.mts` (guards, `json`, `fail`, `seconds`, redaction, request question keys), `tools.mts` (tool specs and input schemas), `input.mts` (input validation), `haiku.mts` (Haiku stand-in and its calibration), `size.mts` (limits, estimate, budget, cut, density), `jev.mts` (`ask`, `answerJev`, endpoint, error text), `registry.mts` (tool registration state). Names below refer to these files. HTTP goes through `$.http.fetch`. Two matcher-less hooks: `session.start` registers the four tools (a failed one is logged via `$.ui.log`) and records the name the engine returned for each (only in the `mcp__<plugin>__<type>` form) next to the default `mcp__jev-api__<type>` names, `tool.call` answers those names and passes every other tool to `next(e)`. A registered tool that no hook answers fails, so never call `next(e)` for `noul`/`choice`/`score`/`batch`, and the hook catches its own throws (a refused `$.env.get`) to answer them too.
- Registration (0.3.2): a tool whose `$.tool.register` failed stays in `missing` and the next hook (session.start or an owned call) registers only those again; registration is a state per tool (`RegState`, `ensureTools`): a tool refused again is retried once at once, then after 5 s, 10 s, ... (max 5 min) and logged once; the wait for a registration is bounded (1 s in an owned call, 5 s in session.start) and paid once per hanging tool (it is then `stuck`: other tools and later calls do not wait for it), so a registration that never answers does not hold a call. The Haiku call carries the dispatch's abort signal. An invalid call is answered before any env read, an already abandoned call sends nothing, and the abort listeners are removed when a call settles. A timed-out or abandoned request is not cancelled (the engine's fetch has no `signal`): callers keep `timeout` at or below their own budget (jevfort: equal to its 4 s budget, 9 s for a compaction ranking). The Haiku output budget (`haikuTokens`) grows with the options and levels the answers list (cap 16384).
- Errors are `{ deny: "<tool>: <reason>" }` (`batch` input errors name the question: `questions[<i>]: ...`): core drops a hook's own `isError` (live on 2.1.322 the model got the error as a normal result), while a `deny` reaches it as an error result.
- `register(on)` has no `$`, so the tools cannot register at module load; `ensureTools($, st, ms)` runs in `session.start` and, best effort, at the start of `tool.call` (a call before session.start still registers). Tools stay deferred (MCP-style, ToolSearch).
- Haiku fallback (0.3.0): after input validation, if none of `TYPESAFE_API_KEY`, `TYPESAFE_BASE_URL`, `JEV_URL` is non-blank, `askHaiku` asks `$.model.complete` (`claude-haiku-5-5`) for `{ answers: { <id>: <answer> } }` JSON and `checkAnswer` rebuilds each answer in the System One shape (noul 0..1; choice must be an option with all option probabilities; score 0..levels-1 with all level probabilities; confidence 0..1), else `<tool>: fallback: ...` (never a made-up answer). A configured Jev that fails stays an error. Not a `claude -p` spawn (decided: effortless and jevfort use the engine call). jevfort raises its budget to 15 s in that case.
- Haiku calibration (0.3.1, measured 2026-11-13 with `claude -p --model claude-haiku-5-5` on the 60 labelled DE/EN effort prompts of the jevfort evaluation, exact plugin questions and state; harness and results were scratch files, not in the repo): raw Haiku overestimated (A2 hit rate 91 of 119 against Jev's 103; mean score for high/xhigh/max prompts 2.71/3.13/3.71 against Jev's 2.4/2.86/3.22) and said 0.8 to 0.93 where Jev says >= 0.95 for mechanical prompts (4 of 24 low prompts >= 0.95, Jev 22). Fixes: (1) `HAIKU_SYSTEM` ends with a calibration paragraph (use the full noul range, spread probabilities, lowest level that fully handles the case, no whole-number scores), (2) `checkAnswer` ignores Haiku's own `score` and derives it as the mean level index of the normalized probabilities (like Jev's expected value; Haiku's `score` was rounded toward whole levels), probabilities normalized to sum 1, (3) `noul` is stretched in logit space by `NOUL_STRETCH` 2.5 (`stretch`). Result over two independent 120-request runs with the shipped prompt and transforms: A2 100 to 108 of 120 (Jev 103), A5 44 to 50 of 60 (Jev 53, criterion 50; raw Haiku 47, so no reliable gain there), mechanical low 17 to 18 of 24 and medium 0 (Jev 22 and 0); run-to-run spread is about 8 hits, so treat the numbers as +-4. Only the effort rubric and the mechanical question were measured; the stretch also applies to every other `noul` (jevfort's take/done/single-action questions), which Jev answers confidently too, but that is unmeasured. Not calibrated: `choice` (its probabilities are only normalized to sum 1, like a score's, since 0.3.2) and the 4-level difficulty rubric.
- Endpoint (only with a variable set): `JEV_URL` > `${TYPESAFE_BASE_URL}/v1/systemone` > `https://api.typesafe.ai/v1/systemone`; an invalid set value is an error, never a fallback. Model `TYPESAFE_DEFAULT_MODEL` or `jev-latest`; timeout via `$.clock.after`, cancelled when the request settles: the call's optional `timeout` input in seconds, else the `userConfig` option `timeout` (`register(on, options)`), else 20 s; a value counts only as a finite number > 0, anything else falls through silently, and above 30 it counts as 30 (`MAX_TIMEOUT_S`: the engine caps one `$.http.fetch` at 30 s itself, and the engine's `$.clock.after` is Bun's setTimeout, which fires a delay past 2^31-1 ms at once); an aborted `next.signal` answers at once. The engine's fetch errors quote the URL (a DNS failure only the bare host), a runtime quotes a rejected header value whole and a server may echo the request into an error body, so `ask()` redacts every error text it passes on (fetch errors and the HTTP error reason: its strings, object keys and numbers, the numbers matched on their source text because `JSON.parse` rounds a 20-digit key, and only when the key is made of number characters: a reviver over every number of a megabyte body took seconds; a successful answer passes unchanged): the URL becomes the variable's name, the host `<host>`, a key of 6 or more characters `<TYPESAFE_API_KEY>`. The bearer key is sent only to an https endpoint; over http the same request goes out without `Authorization`.
- Oversized state (0.4.0, F21; measurements in `docs/tasks/F21-oversized-state-sent-blindly.md`): System One refuses a prompt (state + questions JSON + 26 tokens) of 32768 tokens or more (`n_ctx` 32768) with HTTP 400 `{ error: { type: "exceed_context_size_error", n_prompt_tokens, n_ctx } }` (exact count), and its latency is about `0.7 t + 1.8e-5 t^2` ms for `t` tokens (model `d1-3b`, +-30 %), so the 20 s default timeout fits ~15.6k tokens and the engine's 30 s cap ~21k. `answerJev` (called from the `tool.call` hook for a configured Jev only; Haiku-only calls skip all of it, store included, except that `register.mts` caps their state at 150000 characters with `cutState`) computes `budget = min(n_ctx - 1, timeBudgetTokens(timeoutMs))` (at least 1000 tokens, so a probe-sized timeout is left alone) and refuses before sending only when the OPTIMISTIC estimate `ceil(chars / min(8, 2 * learned density)) + 26` exceeds it; everything else is sent and the server's 400 is the exact oracle (`ask` returns `{ tooBig }` instead of an error). Overflow mode per call: input `overflow` > `userConfig` option `overflow` (invalid: `haiku`, default `haiku`): `error` denies with the numbers and a size to aim for in hundreds of characters; `truncate` cuts the middle (`cutState`: 60 % head, 40 % tail, marker, UTF-16 units, no split surrogate pair) to the budget (limit and timeout) at the learned density and, after a 400, at the exact density its count gave (a dense text such as hex would otherwise still run into the timeout), sends once more and answers a second 400 with the numbers (never a third request; the answer, `batch` array included, does not say it was cut); `haiku` hands the state (cut over 150000 characters) to `askHaiku`. The density (chars per token) is learned from every answer's `usage.input_tokens` and every refusal (samples under 400 tokens ignored, clamped to 1..8, smoothed 0.8/0.2, default 3.0), kept in `$.store` key `density` as `{ v, n }` (read once per instance with a 1 s bound, written fire-and-forget only when it moved over 10 %, a failing store never fails a call). Why `$.store` and not the plugin data dir: live on 2.1.325 `$.env.get("CLAUDE_PLUGIN_DATA")` is undefined inside a mod (`$.store` persists across sessions, checked with two `claude -p` runs). The server's `n_ctx` from a 400 replaces 32768 for the rest of the instance. jevfort passes no `overflow`, so an oversized call of it would be answered by Haiku within its short budget; follow-up: jevfort may want `overflow: "error"`. Constants are measured for one model and one context size; keep them in the constants block.
- The live server answers errors as `{ error: { message } }` (the docs say `{ detail }`; both are read) and wants 2 to 10 score levels.
- Engine pitfalls that shaped the code: no `claude-code` type import, no `any`, no `import()`, no `$.<noun>` passed as a bare value, one matcher-less hook per event, hooks are named function literals; `hooks/*.mjs` is built unmangled.
- Code was copied from jevfort (types, URL regex, request/timeout race), not imported: plugins ship standalone.
- Commands: `pnpm --filter jev-api build`, `pnpm --filter jev-api test`, `pnpm lint`, `claude plugin validate jev-api/plugin`.
- `tests/register.test.mts` has a live smoke block that runs only when `JEV_URL` is set in the shell (plus optional `TYPESAFE_API_KEY`, `TYPESAFE_DEFAULT_MODEL`); never put a URL in the repo.
