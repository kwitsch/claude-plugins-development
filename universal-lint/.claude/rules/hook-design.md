# Hook design (do not "fix" without reading this)

- **Four `command` hooks, one entry:** every event runs `"${CLAUDE_PLUGIN_ROOT}/hooks/lint-file.mjs"` (the placeholder is quoted so a plugin path with a space survives; `claude plugin validate` warns otherwise); `main()` dispatches on `hook_event_name`. No hooks.json `async` flag (the hook itself has an async `main` since 0.15.4, see the stdin sub-bullet), no `statusMessage` (silent), no matcher on the three non-tool events. No `if` or FileChanged matcher filter (F26, Claude Code 2.1.321): `if` takes one rule per handler (46 handlers to keep in step with `EXT_MAP`) and a FileChanged matcher also registers watch entries, matches case-sensitively and cannot skip the hook's own echoes or `unlink`; the saving is ~40 ms background CPU per spawn.
  - PostToolUse `Write|Edit` (`PostToolUse[0]`, index pinned by `tests/manifest.test.mts`): `timeout: 90`, `asyncRewake: true`. Records the content digest (see "File detection"), then lints. A payload without `hook_event_name` is treated as PostToolUse.
  - SessionStart and CwdChanged: `timeout: 30`. Print the watch list on stdout as `{"hookSpecificOutput":{"hookEventName":<event>,"watchPaths":[…]}}`, only when it is non-empty; always exit `0`. CwdChanged builds the list for `new_cwd`; empty output leaves Claude Code with an empty watch list.
  - FileChanged: `timeout: 90`, `asyncRewake: true`. Lints a watched file changed outside Write/Edit with the same findings contract; the text is prefixed `universal-lint (changed outside Write/Edit): ` and `hookEventName` is `FileChanged`.
  - `asyncRewake` runs the hook in the background like `async`, but exit `2` wakes Claude with stderr as soon as the lint finishes, instead of the findings waiting for the next turn. Contract: findings = the `universal-lint…: …` text on stderr + exit `2`; nothing to report = no output, exit `0`.
  - stdin: `main` reads the payload with `await json(process.stdin)` (`node:stream/consumers`), never a synchronous `readFileSync` on fd 0. The `node:process` import (and any `process.stdin` access) opens fd 0 as a non-blocking pipe handle, so a sync read throws EAGAIN whenever the writer is late or the payload exceeds the pipe buffer (about 128-192 KB; Edit payloads carry the whole `tool_response.originalFile`, Write payloads the whole `tool_input.content`), and the fail-open catch made that a silent skip: no lint, no digest (F05, fixed in 0.15.4). A read error or invalid JSON still fails open (no output, exit 0).
  - Invoked directly, no `node` prefix: the built file has a node shebang and the exec bit the build sets. One process per event, no persistent process. `node:crypto` loads lazily (`process.getBuiltinModule`, else `createRequire` on Node < 22.3 / 20.16; floor stays 18.14), about 7 ms off every spawn that never hashes (F26).
  - No debounce of the lint: every Write/Edit lints right away in its own process (user decision 2026-11-06, removed together with the edit coalescing it required). Since 0.16.0 the _report_ of findings (never the lint) is held for the settle window, see "Settle window (F34)" below (user request 2026-11-14). F13 (0.15.12) is, next to F10, the one FileChanged-only exception: a whole-project check is skipped when a completed one started after the file changed (dedup, not a debounce: the first event runs immediately, nothing waits for more events).
- **Command hooks, no MCP server (user decision 2026-11-06)** (kwitsch/claude-plugins prefers a persistent MCP stdio server for hooks, as `dprint` does here):
  - Background lints (`asyncRewake`) remove the one argument for a server (per-event spawn latency): the agentic loop doesn't wait either way. The watch-list hooks are short `git ls-files` calls.
  - Safe because linting never mutates the file: findings arriving after the edit (rewake) cost no correctness. `universal-format` stays synchronous for the opposite reason.
  - Cost: no in-process state. The Write/Edit → FileChanged digest goes through disk (`CLAUDE_PLUGIN_DATA/written/`), the FileChanged concurrency cap uses slot files (`CLAUDE_PLUGIN_DATA/fc-slots/`, see "File detection"), and `onPath` answers persist in `CLAUDE_PLUGIN_DATA/probe-<hashPath(PATH)>.json` (see "PATH probe cache" under "Runtime behavior").
- **No launcher script, no `.mcp.json`:** a direct `.mjs` command hook needs neither; the script always runs under `node`, never `bun`.

## Timeout budget (re-derive when `hooks.json` `timeout` or any `*_TIMEOUT_MS` changes)

- Lint phases: the language's chain tool (`SPAWN_TIMEOUT_MS` 30 s; `CARGO_SPAWN_TIMEOUT_MS` 45 s for cargo; npx route `NPX_SPAWN_TIMEOUT_MS` 55 s) and, for `.ts`/`.tsx`/`.mts`/`.cts` only, `tsc` (`TSC_SPAWN_TIMEOUT_MS` 45 s). Since F18 (0.15.15) they run **at once** (`Promise.all` in `lintResolved`) unless the file's oxlint config has `typeCheck: true`: then `tsc` runs after the chain and only when oxlint did not run (the common case skips `tsc`; never a speculative `tsc`). Each timeout adds up to `KILL_GRACE_MS` (1 s) until the group is dead and the pipes close (see "Process groups"). The hook-level `timeout` is only the backstop that kills the hook process.
- **Settle hold (F34):** after the lint a hold of at most `min(5 s, 90 s - 1 s - uptime)` follows only when there are findings, so the hook-level `timeout` of 90 s is never the reason a finding is lost; the nominal worst cases below are unchanged because the hold shrinks to what is left (87 s FileChanged worst end: 2 s).
- `tsc`'s budget is below the npx one (a stale async finding arrives too late to be useful) and above the single-file one (a whole-project check is slower).
- Nominal worst case, TS file, Write/Edit, concurrent: max(chain 30 s, `tsc` 45 s) + 1 s grace = 46 s (npx chain: 56 s). Sequential fallback (oxlint `typeCheck` config, oxlint unavailable, skip verdict or timeout): chain 30 s + `tsc` 45 s + 2 s grace = 77 s inside the 90 s lint budget; npx chain 55 + 45 + 2 = 102 s (see **Accepted**). Non-TS: one phase, 30/45/55 s + 1 s. FileChanged: see **git** below.
- **Cold npx:** the single bare `npx --yes` attempt gets `NPX_SPAWN_TIMEOUT_MS` (55 s), the npx-fallback branch's worst case.
- **Local bin:** a project-local `node_modules/.bin/<name>` (see "Local `node_modules/.bin` and npx fallback") runs under the chain budget (`SPAWN_TIMEOUT_MS`, 30 s); only an instant spawn failure (ENOENT/EACCES) falls back to npx (via the npx cache), a timeout is not retried, so the worst cases in this section (FileChanged 86-87 s) are unchanged; the npx-cached bin runs under `NPX_SPAWN_TIMEOUT_MS` like npx, so the npx branch's worst case is unchanged.
- Overlapping lints of quick successive edits share the `--tsBuildInfoFile` (accepted, see `typescript-check.md`); FileChanged lints of one tsconfig serialise their `tsc` under the project-check lock (F13).
- **Accepted:** when combined wall time exceeds the 90 s lint budget (cold npx 55 s + `tsc` 45 s + 2 s grace = 102 s, since F18 reached only on the sequential oxlint-`typeCheck` fallback) the hook is killed and that turn's async findings are silently lost. Fail-open, never a wrong result; the next edit's `tsc` hits a warm cache. Since F10 (0.15.9) also accepted: a non-TS npm-chain FileChanged lint (`.js/.jsx/.mjs/.cjs`, `.md`, `.css/.scss`) that gets its slot after process uptime 35 s and runs the npx route (npx-cached bin or bare npx, both under `NPX_SPAWN_TIMEOUT_MS` 55 s) can end past 90 s; it is killed, its lint lost silently (fail open), its slot reclaimed by the dead-pid check.
- **git:** each git call (`git ls-files` for the watch list, `git status` for the FileChanged gate) is capped at `GIT_TIMEOUT_MS` (10 s). FileChanged worst end = max(slot deadline + sequential phases, lock-wait deadline + check timeout) + 1 s grace per phase, every path <= 87 s < 90 s by construction: the slot wait (F10) stops at process uptime 85 s (`FILE_CHANGED_BUDGET_MS`) minus the file's lint reservation, kept as the sum chain + `tsc` although the phases overlap, because the oxlint-`typeCheck` fallback runs them in sequence (`.ts/.tsx/.mts/.cts` 85 − 75 = 10 s, `.rs` 85 − 45 = 40 s, every other lintable extension 85 − 30 = 55 s); the project-check lock wait (F13; `tsc`, go, cargo go through `coalesceProjectCheck`, under the concurrent branch overlapping the chain child) stops at uptime 85 s minus the check's spawn timeout (`tsc`/cargo 40 s, go 55 s) and then runs unlocked. Worst ends: `.ts` concurrent 40 + 45 + 1 = 86 s; `.ts` fallback 10 + 30 + 1 (chain), then `tsc` at once unlocked (past its lock deadline) + 45 + 1 = 87 s; `.rs` 40 + 45 + 1 = 86 s; `.go` 55 + 30 + 1 = 86 s; git's 10 s sits inside the slot deadline. The cold-npx overrun above applies unchanged (a kill loses that lint silently). SessionStart/CwdChanged: git 10 s plus, per listed file until more than `WATCH_LIMIT` lintable in-scope files have been found (where the scan stops; a repo with few lintable files is still scanned in full), the extension filter (no syscall), then one `lstat` per lintable listed file plus one realpath per distinct directory (F12; a symlinked leaf takes a full realpath), inside the 30 s hook timeout.
- **stdin:** read to EOF with no own cap: a writer that never closes stdin holds the process until the hook `timeout` kills it (fail open; before 0.15.4 it got an instant EAGAIN skip). Claude Code closes stdin after the payload (stdin delay at most 9 ms over 50 live events, F05).
- **Backstop and signals (F18):** linter children are detached process groups, so the signal that kills the hook or driver does not reach them by itself; a hook killed with SIGTERM/SIGINT/SIGHUP kills its live groups first (SIGKILL, then re-raises the signal); SIGKILL leaves them to EPIPE at their next write (`tsc` runs to its natural end). Inner timeouts (all < 90 s) make the backstop reachable only through a hung stdin writer or an external kill.

## Runtime behavior (`lint_file`)

- Every guard failure, clean result, skip (crash/misconfig) or missing tool returns `{}` silently (fail open); only issues produce a truncated findings text (`lintFileHandler` returns it as `additionalContext`; `main` writes it to stderr and exits 2). The guard chain lives in `resolveLintTarget`/`lintFileHandler`.
- **Process groups (F18, 0.15.15):** every linter/tsc child runs through `spawnGroup` (`child_process.spawn`, `detached: true`, stdin `/dev/null` as before); timeout = SIGTERM to the group, SIGKILL after `KILL_GRACE_MS` (1 s); output capped per stream at `MAX_BUFFER_BYTES` (10 MiB; ENOBUFS kills the group, further chunks discarded); the result has spawnSync's shape (`error.code` ETIMEDOUT/ENOENT/EACCES/ENOBUFS, `signal`, `status`) and every classification is as with spawnSync; the result is taken on `close` (both pipes closed, so a killed tree is reaped before the lint continues), timers cleared only then; one SIGTERM/SIGINT/SIGHUP handler per process SIGKILLs the live groups and re-raises (see "Timeout budget"). POSIX only (`process.kill(-pid)`; the hook runs through a shebang `.mjs`). Residuals: a grandchild that called `setsid` leaves the group and, holding a pipe, delays `close` until the hook backstop (same as spawnSync); the pid-reuse window between the leader's reap and `close` is microseconds and needs a pid wraparound; two heavy children at once (eslint + tsc) per lint, so a FileChanged burst may run 2K children (`FILE_CHANGED_SLOTS` bounds lints, not children).
- Selection (`selectLintTool`): the first chain tool on `PATH` wins, else the first npm chain tool with a project-local bin, else the first npm chain tool via npx; there is no per-file style-conflict skip (a linter needn't reproduce exact output the way a formatter does). The plugin does not rewrite PATH (it would change which tools are found); on WSL the Windows-PATH cost now sits only inside child processes (`go vet`'s gccgo PATH scan, ~95 ms per run), the hook-side real-vs-/mnt gap shows no /mnt penalty (largest median difference 15 ms, real PATH faster), measured 2026-11-10 on 0.15.25 (F28 doc, Evidence).
- **PATH probe cache (F11, 0.15.10):** `onPath` answers persist in `${CLAUDE_PLUGIN_DATA || os.tmpdir()}/probe-<hashPath(PATH)>.json` (full 64-hex sha256 of the PATH string, so a PATH change changes the file name), format `{"hits": {"<tool>": "<absolute dir>"}, "misses": {"<tool>": <Date.now() ms>}}`. The first `onPath` call of a process reads the file once (`loadProbeStore`; an unreadable, corrupt or wrongly shaped file is an empty store). A hit is re-validated with one `accessSync(<dir>/<tool>, X_OK)` plus `statSync(...).isFile()` (a directory named like the tool is no hit, in the scan too); failure runs the full PATH probe and replaces the entry. A miss is valid while `0 <= Date.now() - at < PROBE_MISS_TTL_MS` (`PROBE_MISS_TTL_MS`, 10 min; a future-dated miss counts as expired, as the npx stamp does), with one time per entry so a rewrite never extends older misses. Otherwise the full PATH probe runs and the result is written back (`saveProbeStore`: temp `<file>.<pid>.tmp` + `renameSync`, every error swallowed: the next process probes again); a warm process writes nothing. Concurrent writers: last writer wins, an entry another process added after this one loaded the file can be dropped (cost: one probe later); no locking. Selection order and bare-name spawns are unchanged: the stored dir is only re-validated, never spawned. Residuals: a cached miss hides a newly installed tool for up to 10 min, also an earlier chain tool (a later chain tool, a local bin or npx runs meanwhile; remedy: delete `probe-*.json` from the data dir); a copy of a tool added to an earlier PATH dir is not noticed (presence only, the bare-name spawn still runs PATH's first one); a tool reachable only through a relative PATH entry (`.`, `bin`) is cwd-dependent: never cached as a hit, and its miss is per PATH string, not per cwd; in the `os.tmpdir()` fallback the file is shared by all users with the same PATH string (a planted hit only says "present" for a tool executable in the planted dir, a planted miss suppresses that tool's lint for its TTL; same class as `written/`); the `<pid>.tmp` temp name shares the F10 pid-namespace residual (two containers on one data dir can collide; cost one lost write, never a torn file); probe files are never pruned (one per distinct PATH string, a few hundred bytes).
- Go entries target the edited file's **directory** (`go vet`/`golangci-lint` are package-scoped); checkstyle gets `-c <resolved config>`.
- **Config walks (F20, 0.15.17):** walks probe through `configExists`. On a path lexically under `/mnt/` (no realpath) one memoized `readdirSync` per directory prefilters names (upper-cased first segment), hits confirmed by `existsSync`, readdir errors fall back to `existsSync`; memo per process, never invalidated; the skill driver's batch sees one listing per directory. ext4 unchanged.
- stdout+stderr are captured and **never ignored**, unlike the formatter sibling: the findings text IS the payload. `maxBuffer` is raised well above the 1 MB default for the same reason — a noisy linter's output would otherwise truncate as ENOBUFS.
- Success is **classification, not a content diff** (the file is never modified): `classifyExit` applies each tool's documented exit-code contract.
- **Exception: `checkstyle`** is classified by output (`classifyCheckstyleOutput`): its exit code counts only `error`-severity violations, and the bundled default ruleset (and many real projects) run at `warning` — exit-code classification would silently miss real findings.
- `stylelint` (CSS/SCSS) does not share the 0-clean/1-issues contract: `0` clean, `2` real lint problem, anything else (`1` fatal, `64` bad usage, `78` bad config) skip (stylelint.io CLI docs). A `.css`/`.scss` file without a stylelint config never reaches it: `lintResolved` skips the chain before any PATH probe, local-bin lookup or npx (`languages.md`, F07, 0.15.6).
- `yamllint` runs without `--strict`, so warnings-only findings don't surface — consistent with `eslint` (warnings don't affect its exit code either).

### Local `node_modules/.bin` and npx fallback

- `eslint`, `oxlint`, `markdownlint-cli2`, `markdownlint` and `stylelint` (the chain entries with `npmSpec`), when absent from `PATH`, run the nearest `node_modules/.bin/<name>` from the file's directory up to `cwd` inclusive (`localBin` over `walkUpToCwd`; directories outside `cwd` never count), keyed by bin name (`markdownlint`'s package is `markdownlint-cli`) (user decision, F04, 0.15.3; `tsc` keeps its own cwd-only lookup, see `typescript-check.md`).
- The local bin is spawned directly from its package root (the directory holding the selected `node_modules`: the payload `cwd` or a sub-package; `Finding.base` follows it, the target and the edit-range gate stay `cwd`-relative; the file argument is absolute) and the bin's directory first on the child's `PATH`, as npx does: oxlint 1.91 finds `tsgolint` only on `PATH` or in the spawn cwd's `node_modules/.bin`, else it exits 1 with "Failed to find tsgolint executable", a false finding.
- The package-root spawn cwd exists because eslint <= 9 resolves its flat config from the spawn cwd, so a sub-package eslint finds the sub-package config. Residual (same as 0.15.2): an eslint <= 9 bin at the `cwd` level with a config only in a sub-directory still resolves from `cwd`.
- A local bin that cannot spawn (ENOENT/EACCES, e.g. no exec bit or a missing shim interpreter) falls through to the npx route below (npx cache, then npx); a timeout does not (no second budget).
- **npx cache (F09, 0.15.8):** without a local bin, and when no `node_modules/.bin/<name>` exists from the spawn cwd up to `/` (npx would run that one first, so that case is left to npx), the bin npx installed for the package, `${npm_config_cache || NPM_CONFIG_CACHE || ~/.npm}/_npx/<sha512(package) hex[0:16]>/node_modules/.bin/<name>` (npm 7+ layout, key verified on npm 11.19.1 for all five packages), runs directly like a local bin (`runNpx` through `spawnBin`: bin dir first on PATH, npx's cwd, npx budget, ENOENT/EACCES -> npx), unless npx holds the dir's `concurrency.lock` (install in progress) or the refresh stamp `${CLAUDE_PLUGIN_DATA || os.tmpdir()}/npx-refreshed-<key>` is missing, older than 24 h (`NPX_REFRESH_MS`) or dated in the future (clock jump, synced data dir). Otherwise `npx --yes <package> ...` as before (each package ships the one bin the chain entry names (`markdownlint-cli` -> `markdownlint`), so the single-positional idiom is safe; `npx` is assumed present since the hook already runs under node), and every npx run that spawned (no spawn `error`, any exit status) renews the stamp (errors swallowed); the above-cwd npx run never touches the cache and renews nothing. Saves about 0.5-0.8 s of npm startup per lint (F09, 0.15.8).
  - Staleness: npx checks a name-only spec against the registry's `latest` on every call (npm 11.19.1 `libnpmexec` `getManifest` with `preferOnline: true`); the direct route does so at most once per 24 h, through that stamp-renewing npx run, so the hook can lag a new release by up to a day. A plugin-data stamp, not the `_npx/<key>` dir mtime, marks the last refresh: `libnpmexec` ships `with-lock.js` (whose `concurrency.lock` bumps the dir mtime on every npx run) only from 10.2.0 (npm 11.x); on Node 22 LTS's npm 10.9 the dir mtime moves only on installs, so an mtime-based route would silently decay to zero gain 24 h after an install.
  - Trust and output: the cached bin is the one `npx --yes <package>` runs from its own cache; the hook only reads the npm cache, never writes it. The direct route passes no `npm_*` variables (the linters read none) and prints no npm notices (F24's noise is gone on this route). The bare `npx --yes` route sets `npm_config_update_notifier=false`, `npm_config_fund=false`, `npm_config_audit=false` (F24, 0.15.21) and leaves loglevel alone so install errors still show.
  - Residuals: a cache root set only in `.npmrc` is a miss (npx runs), but when an old `~/.npm/_npx/<key>` from before the move exists, that old copy runs while the stamp is fresh (npx refreshes the other cache; remedy: remove `~/.npm/_npx`); npx also prefers a bin declared by the cwd's own `package.json` (working inside the linter's own repo) and a global npm bin (`<prefix>/bin/<name>`), which the hook catches only when that dir is on PATH (selection pass 1), so in those cases the cached copy runs instead; the `concurrency.lock` guard is a no-op on npm 10.x and older (`libnpmexec` < 10.2.0 has no lock) and a TOCTOU check anyway (an external npx install that starts right after it can replace the tree under a running cached bin; accepted); a changed npm cache layout is a miss (npx, no gain, no harm); concurrent stale-stamp lints all go through npx until the first one renews the stamp.
- Trust: (1) a bin in `<cwd>/node_modules/.bin` is the one `npx` runs today (npm's own lookup starts at cwd); (2) a sub-package bin between the file and cwd is a new execution surface of the same trust class (the project tree the user asked to lint), never above cwd; (3) the local route never runs a bin above cwd, so where an in-tree bin exists, an above-cwd bin that npx's own walk would have reached instead is no longer run. Without an in-tree bin, the hook resolves `<name>` as npx does: an above-cwd `node_modules/.bin/<name>` (npm 11.19.1 walks from cwd up to `/`, probed) is left to npx itself, otherwise npx's own cached bin runs directly (npx-cache route above), the same trust class as `npx --yes <package>` and any `npx` the user runs; the above-cwd route is deliberately not blocked, since that would drop lint for a monorepo sub-package session whose linters sit at the monorepo root (user decision, F04, 0.15.3).
- `yamllint` has no npm package (PyPI only); `ruff`, `golangci-lint`, `go`, `ktlint`, `checkstyle` and the Rust/PHP tools have no safe npm equivalent either.

## Edit-range gate

- After an `Edit` the hook exits 2 only when a diagnostic is not proven to sit in the edited file outside the edited lines. No registered tool (shellcheck, checkstyle, ktlint, eslint, oxlint, ruff check, golangci-lint, go vet, yamllint, markdownlint(-cli2), stylelint, phpstan, psalm, cargo clippy/check) nor `tsc` has a line-range check mode (`golangci-lint --new-from-rev`/`psalm --diff` are git-based; `ruff format --line-range` is not a check), so the scan stays file/project-scoped and `gateFinding` filters the raw text afterwards. `buildArgv`/`classifyExit` are unchanged.
- **Range source:** the Edit `tool_response.structuredPatch` hunks (`editRanges`, inclusive 0-based lines): each run of `+` lines; a run of only `-` lines (pure deletion) gives the two lines around the deletion point, so deletions are linted too. `\ No newline at end of file` is not a line.
- **Whole file:** `Write`, any non-`Edit` tool, or a missing/malformed `structuredPatch`. An empty patch (nothing changed) returns `{}` without linting.
- **Location extraction**, per line after stripping `ANSI_SGR_RE`; first match wins:
  - A `LOC_PATH_RE` `<path>.<ext>[:(]<line>`: ruff, ktlint, golangci-lint, go vet, checkstyle `[WARN] /abs/A.java:3:`, markdownlint `a.md:12`, psalm, oxlint `,-[src/a.ts:3:7]`, cargo `--> src/a.rs:12:5`, tsc `a.ts(12,5)`/`a.ts:12:5` (match anchored at a token start by a lookbehind; the unanchored form was quadratic on a long line, F27)
  - B `LOC_ROW_RE` `  <line>:<col>  ` rows (path-less, own file): eslint stylish, stylelint stylish, yamllint standard.
  - C `LOC_SHELLCHECK_RE` `In <file> line <n>:` (path-less, own file): shellcheck's default tty format.
- **Base directory** (`Finding.base`, set in `runChainLint`/`runTypeCheck`): cargo → directory of the `--manifest-path` Cargo.toml; golangci-lint/go vet (`targetsDir`) → the edited file's directory; tsc and every other tool → the spawn cwd: the payload `cwd`, or the directory holding the selected local `node_modules`.
- **Path matching (user decision):** (1) `path.resolve(base, p) === resolved` → own file; (2) else, only for a relative `p` whose base-resolved path does not exist, a path-segment suffix match (`resolved.endsWith(sep + p)`) → own file (covers cargo workspace-root paths, cwd-relative go paths); (3) else **foreign**: kept and reportable. Diagnostics in other files (e.g. tsc errors elsewhere) therefore still exit 2.
- **Filtering** by blank-line paragraphs: a paragraph without a located line is kept but not reportable (headers, summaries); otherwise it is split into segments at located lines (each carries the unlocated lines after it, so tsc continuation lines stay with their diagnostic; earlier lines are the preamble). Own-file misses are dropped, hits and foreign segments kept; a paragraph whose segments are all dropped loses its preamble. Exact lines, no context slack.
- **Result:** no located line at all → finding unchanged (fail open = report: phpstan's table format); nothing reportable left → finding dropped; exit 2 only when at least one finding survives. The gate runs before `truncate()`.
- **Parse errors are always kept:** an own-file miss whose segment or paragraph preamble matches `PARSE_ERROR_RE` (parse/syntax error wording, `unclosed`, `unterminated`, `end of file`, rustc's unnumbered `error: expected` header (not a bare `expected '...'`, which eslint eqeqeq and rustc E0308 also print), tsc `TS1xxx`, shellcheck `SC1xxx`) stays reportable, since an edit-caused parse error is often reported away from the edit (unclosed brace → EOF). Other own-file diagnostics outside the edit (e.g. a tsc call-site error in the same file) are dropped by design.
- **Residuals:** a parse error phrased outside `PARSE_ERROR_RE` is gated; a path containing a space is not matched and counts as foreign (kept); a same-named file reached only by the suffix fallback can be mistaken for the edited file; a format the regexes miss is reported unchanged.

## File detection (FileChanged + watch list)

- **Scope (`scopedTarget`, port of dprint's `realish`/`inScope`), shared by every event** (PostToolUse through `resolveLintTarget`, the skill driver through it, FileChanged, the watch list): the path resolved against the payload `cwd` (never `process.cwd()`) must exist, have a lintable extension (`EXT_MAP` or `TYPE_CHECK_EXTS`), its real path must lie strictly inside realpath(cwd), not be excluded, not lie inside realpath(`scratchpad_dir`) when the payload has one, and not be a dangling link. The lint keeps the lexical path; the real path is the digest key. A Write/Edit through a symlink pointing outside the cwd, or into a scratchpad inside it, is not linted.
- **Watch list** (`watchList`, SessionStart/CwdChanged): `git ls-files -co --exclude-standard -z` (tracked + untracked-not-ignored) in the cwd (`new_cwd` for CwdChanged), filtered through `scopedTarget` with a per-call directory realpath memo (`roots.dirs`, F12: one `lstat` per lintable entry plus one JS `realish` per distinct directory; scope semantics unchanged). The directory memo holds for one `watchList` call, so a directory replaced by a symlink during the scan keeps its earlier real path for the files after it (today each file re-resolves). Harmless: `watchPaths` is only the subscription list; every FileChanged re-runs `scopedTarget` without the memo before linting. The scan stops at the first file that makes more than `WATCH_LIMIT` (5000) distinct lintable in-scope files: nothing is watched and stderr gets a "more than 5000 files" note (no exact count; the rest of the list is not scoped, `git ls-files` itself still runs to completion); a git failure (not a repo, no git, timeout) watches nothing.
- **FileChanged skip order** (`fileChangedHandler`, first match wins, every skip = `{}`): `unlink` event; out of scope; content equals the digest Write/Edit recorded; `git --no-optional-locks status --porcelain --untracked-files=normal --ignored=matching -- <fp>` (cwd `dirname(fp)`) prints nothing (tracked, unchanged) or starts with `!!` (ignored). A git failure lints. `add` and `change` are handled alike. Then the slot gate (below).
- **Slot cap (F10, 0.15.9):** after the git gate, `fileChangedHandler` takes one of K = `FILE_CHANGED_SLOTS` = `max(2, floor(os.availableParallelism() / 4))` slots (3 on 12 cores) through `acquireSlot`: slot files `${CLAUDE_PLUGIN_DATA || os.tmpdir()}/fc-slots/<i>`, claimed by `writeFileSync(slot, pid, { flag: "wx" })` (an exclusive create, not temp file + `renameSync`: the claim must fail when held). A slot is stale (`slotStale`, removed before the claim) when its pid is dead (`process.kill(pid, 0)` throws ESRCH) or its mtime is at least 90 s (`HOOK_TIMEOUT_MS`) old or at least 90 s in the future (the future side has a tolerance because a fresh slot's sub-ms mtime can be ahead of integer `Date.now()`); EPERM and an empty or unparsable pid count as held until the mtime rule. While all K are held it polls every 100 ms (`Atomics.wait`) until process uptime reaches `FILE_CHANGED_BUDGET_MS` (85 s) minus the file's lint budget: `.ts/.tsx/.mts/.cts` 10 s, `.rs` 40 s, every other lintable extension 55 s (see "Timeout budget"); one full round over the slots always runs first. No slot in time: `{}` plus the stderr note `universal-lint: FileChanged: no lint slot free in time, <path> not linted`, exit 0 (never rewakes). Any other slot error (mkdir, create, stale removal) lints without a slot (fail open, as before F10). Release: `rmSync` in a `finally` around `lintResolved`, inside its own `try` so a failed release never discards findings; the settle hold (F34) comes after the release, so a held finding never keeps a slot. FileChanged only: PostToolUse Write/Edit and the skill driver take no slot and never wait (no-debounce user decision 2026-11-06). Residuals: the stale-reclaim race may briefly allow K+1 lints; a wall-clock jump of 90 s or more makes live slots look stale; a reused pid holds a dead slot until the 90 s mtime rule; no FIFO among waiters; the cap counts lints, not the waiting hook node processes nor their `git status` children (each waiting hook's git gate runs before the slot gate, so git children are not bounded by K); since F18 a `.ts/.tsx/.mts/.cts` lint without an oxlint `typeCheck` config runs its chain tool and `tsc` at once, so up to 2K heavy children run per burst (a CPU-starved `tsc` that hits `TSC_SPAWN_TIMEOUT_MS` skips, fail open); a slot per child was not chosen because it would halve the lint throughput of the common oxlint-`typeCheck` case, which runs one child; a timed-out check's whole process group is killed (SIGTERM, SIGKILL after 1 s; F18) and a holder killed with SIGTERM/SIGINT/SIGHUP kills its live groups first, but a holder SIGKILLed by the 90 s backstop leaves its detached children to finish on their own; every session using the same data dir shares the K slots, and the tmpdir fallback shares them across users (another user's slot dir makes lints fail open); a data dir shared across pid namespaces (e.g. a container and its host) makes a live holder's pid look dead (`process.kill` ESRCH), so its slot is reclaimed and K+1 lints run; a file `lintResolved` would not lint anyway (no eslint/oxlint/stylelint config, no tool found) still takes or waits for a slot and can get the give-up note.
- **Project-check lock (F13, 0.15.12):** FileChanged only (`coalesce` from `hookEventName` in `lintResolved`). `coalesceProjectCheck` wraps the `tsc`/`go vet`/`golangci-lint`/`cargo` spawn: `fc-locks/<key>.lock` (`wx` + pid, `slotStale`) and `.last` (`Date.now()` before the spawn, written after a run without error/signal); key = `hashPath(tool:tsconfig|package dir|Cargo.toml)`. Skip when `ctime(file) < .last <= Date.now()`, checked every 100 ms while waiting and once after the claim. Taken after the slot (held while waiting); at uptime `FILE_CHANGED_BUDGET_MS` − spawn timeout, or on any error, it runs unlocked. Residuals: drvfs/9P clock skew covers too early (lost finding) or late (extra run); coarse ctime tick vs `Date.now()`; a holder killed after `.last` loses the report; the report targets the tsconfig dir/package/crate; slot-cap stale-reclaim/data-dir/pid-namespace residuals.
- **Digest store:** PostToolUse records the SHA-256 (base64) of the file on disk at `${CLAUDE_PLUGIN_DATA || os.tmpdir()}/written/<hashPath(real path)>` (temp file + `renameSync`, one file per real path, no locking) before it lints. A missing digest is no match; a write error is swallowed (cost: one duplicate lint). The skill driver records nothing. No pruning (bounded by the number of files ever written). Race: a FileChanged delivered before the digest lands lints twice (duplicate findings, never lost ones); measured 0 of 55 echoes missed, race margin p50 600 ms (F32). Hashing is unbounded by file size by design (about 11 ms per 10 MB, 250 MB RSS at 200 MB; F25 closed docs-only): a size skip would make FileChanged lint the file, and a lint skip is a policy change (F19).
- **FileChanged lints the whole file:** no edit-range gate (`ranges = null`).
- **Static watch list (dprint F24, F15):** files created after SessionStart/CwdChanged are not watched until the next SessionStart/CwdChanged. A watched file replaced by unlink+create (checkout, restore) keeps its watch unless Claude Code reported it as `unlink` (2.1.319, flat 50-file repo: 1 and 3 of 50 in two runs; table in F15). Re-emitting the list from FileChanged cannot re-arm them: `watchPaths` on FileChanged stdout is honoured under `asyncRewake`, but the watcher is re-created only when the sorted list changes, and a changing list drops events during the checkout (F15, docs-only). Refreshing after Bash commands is a follow-up.

## Path exclusions (`isExcludedPath`)

- Skips `node_modules/`, `vendor/`, `.git/`, plus two Claude-Code-owned subtrees that can land inside a broad `cwd` (e.g. `$HOME`, or a repo root nesting worktrees): `.claude/worktrees/` (harness-created git worktrees, never this session's own content) and `.claude/agent-memory/` (gitignored agent runtime artifacts).
- Any basename containing `.local.` (e.g. `settings.local.json`) is skipped in any directory, matching `.claude/.gitignore`'s `*.local.*` personal-override convention.
- **Deliberately narrow — not a blanket `.claude/` exclusion.** Tracked content under `.claude/` (`rules/`, `agents/`, `skills/`, `settings.json`) must keep getting linted; a `.claude/rules/*.md` edit still triggers markdownlint.
- Exclusion is checked on the path relative to the **real** cwd (inside `scopedTarget`), so a symlinked cwd or file cannot dodge it.
