## Settle window (F34, 0.16.0)

User request 2026-11-14: a finding that a following edit already repaired must not wake Claude. Narrows two earlier decisions (F23: no superseded-lint drop, no PostToolUse wait; no debounce, 2026-11-06): only the **report** of findings is held, the lint itself still starts at once and clean lints never wait; a finding is dropped only when a later edit rewrote exactly the line it sits on.

- **Contract.** A lint (PostToolUse Write/Edit, FileChanged) that ends with findings holds them for `SETTLE_MS` (5000 ms from the end of the lint). Afterwards the diagnostics located in the linted file on a line that a later edit of the file removed or replaced are dropped; the later edit's own lint reports what persists there (so a reproduced error is reported by that edit, a repaired one by nobody). Everything else is reported as before. Diagnostics in other files, findings without a located line (phpstan tables) and any case that cannot be judged are never dropped (fail open): no own record, unreadable or missing journal or record, no record matching the digest anchor, the file changed while the linter ran, a later Edit record whose `before` is not the digest of the record before it (an unjournaled change in between, e.g. `sed -i` on an unwatched file: its hunks are in other coordinates; a CRLF file's LF `originalFile` never matches either, also fail open). F35 (0.16.1): findings the filter cannot drop (foreign-file or unlocated text only; checked with `gateFinding(f, () => false, resolved, "drop")`) are returned at once, without the hold.
- **Journal** `${CLAUDE_PLUGIN_DATA || os.tmpdir()}/settle/<hashPath(real)>-<15-digit ms>-<pid>.json` = `{hunks: EditHunk[] | null, digest, before}` (`before` = sha256 base64 of the Edit's `tool_response.originalFile`, the content its hunks apply to; null for Write/FileChanged): one per Write/Edit lint (`lintFileHandler`, after the scope and empty-patch checks, before linting, also for clean lints) and one per FileChanged whose digest check says the content changed outside Write/Edit (`fileChangedHandler`, before the git gate and the slot wait, with `hunks: null`). The digest-matched echo of a Write/Edit records nothing. Temp file + `renameSync`; the writer prunes entries whose name timestamp is more than `HOOK_TIMEOUT_MS` away from now, past or future (a clock stepped back would otherwise leave a stale record sorting after every fresh one, read as a later edit).
- **Lines.** `EditHunk` = the `structuredPatch` hunk plus `map` (new 0-based line of each old line, -1 when removed); `carryLine` maps an old line through one edit (before the hunk unchanged, inside it by `map`, after it shifted by the summed `newLines - oldLines`; a hunk without old lines names the line before it). `hunks: null` (Write, FileChanged, malformed patch) touches every line. Supersession = `gateFinding(f, line0 => carried through every later record never gives null, resolved, false)`: per diagnostic, parse-error exception off.
- **Coordinates.** The finding's lines are those of the file as the linter read it. The lint reads `d0 = digest(file)` before it spawns anything and `d1` after it ended; `d0 !== d1` (an edit landed during the lint) = no supersession. Otherwise the reference record is the last journal record whose digest equals `d0`; only the records after it count. No match: no supersession. The anchor does not rely on process start order.
- **Hold outside every lock.** `lintResolved` returns the gated `Finding[]`; `settleFindings` holds and filters; `formatFindings` builds the text. FileChanged runs `lintResolved` inside the slot `try/finally` and settles after the release; the project-check lock is released with its spawn; PostToolUse takes neither. So a held finding never occupies a slot or a lock.
- **Hold length** `settleWaitMs()` = `min(base, HOOK_TIMEOUT_MS - 1000 - uptime)`, never negative, so the longest FileChanged path (87 s, "Timeout budget") ends before the 90 s backstop. `base` = `SETTLE_MS`, or the env seam `UNIVERSAL_LINT_SETTLE_MS` (a finite number >= 0; used by the tests and `scripts/perf.mts` with 0; not a user setting, the plugin has no toggle, CLAUDE.md).
- **Verified live (Claude Code 2.1.325, interactive via tmux, stub shellcheck, hold 15 s):** Write with a flagged line, then an Edit of that line 1-2 s later: no wake; an Edit of another line: the finding wakes Claude 16 s after the Write. Interactive hooks show `moved to the background (3ms)`.
- **Residuals.** (1) `claude -p` (headless) does not background `asyncRewake` hooks (2.1.325, debug log "Slow PostToolUse hooks: 46026ms for Write", the next tool call waits for the hook): there the hold delays the turn by up to `SETTLE_MS` per lint with findings and can never be superseded (the loop is parked, no edit can come); the finding reaches the model in the same turn as before. (2) A later edit whose hook dies, times out, finds no tool or gets no FileChanged slot loses the earlier finding on the touched line (F23's residual, accepted by the request). (3) An edit landing while the linter runs disables the supersession for that lint (its findings are reported as before); slow linters (tsc) see this often. (4) Line numbers in a finding reported after the hold can be stale by lines inserted above during the window. (5) A synchronous formatter hook (universal-format) that rewrites the file after the record's digest was taken leaves no record matching `d0`: reported as before. (6) A burst of N Edits with findings parks N node processes for up to 5 s each (no child processes). (7) Foreign-file and unlocated findings can be reported twice (by the held lint and by the later edit); duplicate suppression stays rejected (F23). (9) A late FileChanged echo whose digest has not landed yet journals a whole-file edit and can drop held findings (the FileChanged lint re-reports them). A held own-file parse error is dropped by any later edit (F36: it is reported away from its cause, and every later lint reports a persisting parse error itself). (8) Journal order is the file-name order (ms, then pid): same-millisecond edits from two processes order by pid. The order is the time each hook wrote its record, not the edit order: a hook that starts late can read the file after a later edit landed and journal after that edit's hook. Its record then shares a digest with a later record, so two records after the anchor with one digest mean "cannot tell" (reported as before).
