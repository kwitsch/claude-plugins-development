# taskflow

Spec-driven design and delivery pipeline: `/taskflow:build-task` (design: explore, size, design, spec; delivery: plan, wave-parallel implement, review, ship), `/taskflow:dispatch-task` (runs build-task in a background worktree session) and `/taskflow:review-task` (commits, simplifies and code-reviews a branch), plus the internal skills `taskflow:design-task`, `taskflow:spec-task` and `taskflow:plan-task` (build-task's design, spec and plan steps) and `taskflow:decide`, which makes every build-task, design-task, review-task, spec-task and plan-task decision (interactive or `--headless`). Hand-written plugin files live in `assets/` and are copied to `plugin/` by `pnpm --filter taskflow build`; the one script is built from `src/bin/ship-ensure-mergeable.ts`, and the one mod `src/hooks/register.ts` (tool `size-task`, pure helpers in `size.ts`, types in `types.ts`) is built to `plugin/hooks/register.js`.

## Boundary rule

The plugin ships these components:

- `assets/skills/build-task/` — inline orchestrator skill. Creates a `feature/<slug>` worktree and calls `EnterWorktree`, routes every decision through `decide`, owns the whole pipeline (design and delivery) and runs its design, spec and plan steps through `design-task`, `spec-task` and `plan-task`, runs `review-task` as its Review step.
  - Five scripts in `assets/workflows/` (`build-task-<name>.workflow.js`), run by name via `Workflow({name: "taskflow:build-task-<name>", args})`, never `scriptPath` ([why](../development/wiki/plugins/taskflow/design/workflows.md)): the design pipeline `build-task-design.workflow.js` (explore, size and design in one script) and `build-task-spec.workflow.js`, and the delivery pipeline `build-task-plan.workflow.js`, `build-task-implement.workflow.js`, `build-task-ship.workflow.js`. They leave session-temp files (`explore-<slug>.md` and `draft-<slug>.md`, `spec-<slug>.md`, `plan-<slug>.md`, `implement-<slug>.json`, `pr-body-<slug>.md`) and return only their paths plus the small fields the skills' checkpoints and final report need. The skills never read those files: they thread their absolute paths into the later scripts, whose agents read them. Step 4.3 runs `taskflow:review-task` via the `Skill` tool and then writes `review-<slug>.json` itself. build-task runs implement and ship directly; `design-task` runs `build-task-design.workflow.js`, `spec-task` runs `build-task-spec.workflow.js` and `plan-task` runs `build-task-plan.workflow.js`.
  - Ten of the plugin agents are build-task roles (`designer`, `design-reviewer`, `planner`, `spec-writer`, `worktree-merger`, `pr-author`, `shipper`, `ci-monitor`, `ci-fixer`, `explore-scribe`), dispatched by the scripts via `agentType: "taskflow:<name>"`; the script's `model` option overrides the frontmatter model, so size-driven models (designer, planner) still work.
  - Tool hints: the skill probes graphmind and jev-api once (step 2.1) and passes `GRAPHMIND_AVAILABLE`/`REPO_PATH`/`JEV_AVAILABLE` to the scripts, which append a hint to the prompts of agents that benefit — graphmind: designer, design-reviewer, implementer/reviewer/fixer, ci-fixer (plus explorers and planner); jev-api (its single `request` tool): planner (task complexity via a `score` question), ci-monitor and ci-fixer (failure classification via a `choice` question). Absent tool ⇒ no hint, prompt unchanged. `design-task` probes graphmind itself for the design script, and `plan-task` probes graphmind and jev-api itself, with the same probes, for the plan script.
  - Size (`S`/`M`/`L`/`XL`, once per design-task workflow run, in the `Size` stage of `build-task-design.workflow.js` after the explore stages): an inline haiku agent calls the mod tool `mcp__taskflow__size-task` (`src/hooks/register.ts`), which does all of it: jev-api's `request` with a calibrated `choice` question at `probabilities[choice] >= 0.5`, else a plain model call (`FALLBACK_MODEL`) with the same descriptions; the agent's own reasoning is only the safety net when the tool is missing or errors, and no result twice means `M`. Wording, threshold and model are measured: [size-calibration](../development/wiki/plugins/taskflow/design/size-calibration.md); do not change them without re-running it. Every size-driven choice comes from it: the designer model (resolved in-script after the Size stage, and by design-task's direct designer dispatch), the planner model (resolved in-script from the `SIZE` arg) and the review level (build-task passes `--size=<SIZE>` to `review-task`, which alone maps it to the `code-review` level).
  - Prompts for roles without an `agentType` (scout, explorers, memory recall, size agent, plan checker, implementer/reviewer/fixer, result-file scribe) are inline.
- `assets/skills/design-task/` — inline internal skill, SKILL.md plus its usage ref `workflows/design.md`: build-task's step 2. Contract `[--headless] <task prompt>`; it probes graphmind, derives `explore-<slug>.md`/`draft-<slug>.md` with build-task's slug rule and runs `build-task-design`, which returns `complete` or `blocked` with decide-ready questions. Every `blocked` goes through `decide`: a re-explore answer (`Re-run explore`, or any answer to the `explore` question) re-runs the whole workflow with the focus and every earlier decision in `TASK`; every other answer, and every intent correction, dispatches only `taskflow:designer` via the Agent tool (`subagent_type`, size-keyed model with the fable → opus fallback, JSON final message with the contamination check), without the design reviewer. It runs the intent acceptance. Headless: at most 3 re-runs (full re-runs plus designer dispatches). Last line `RESULT: {json}` (`explorePath`, `size`, `designPath`, `findings`) or a `design-task:` stop line. [Why](../development/wiki/plugins/taskflow/design/design-task.md).
- `assets/skills/dispatch-task/` — one-step skill that dispatches `build-task` into a worktree-isolated background session. Self-contained by requirement: no reference to any other plugin, its own copy of the `claude --worktree … --bg` mechanics. Constraints: rule `dispatch-task.md`.
- `assets/skills/review-task/` — inline, model-invocable review skill, SKILL.md only (no workflow script). Commits pending changes (`git add -A`), then runs Claude Code's bundled `simplify` and `code-review <level> --fix` over `<base>...HEAD`, one commit per pass. `--size` → level: `S` → `medium`, `M` → `high`, `L` → `xhigh`, `XL` → `max`; without `--size` it sizes the branch via `mcp__taskflow__size-task` (own reasoning as fallback). Refuses a detached HEAD and the base branch; never pushes. [Why](../development/wiki/plugins/taskflow/design/review-task.md).
- `assets/skills/decide/` — inline, model-invocable decision skill, SKILL.md only. Interactive: one `AskUserQuestion`; with `--headless`: the `advisor` tool when it is in the tool list, else the `taskflow:decider` agent; never `AskUserQuestion` in headless. Called by build-task, design-task, review-task, spec-task and plan-task, which forward `--headless`; prints the content as bullets and ends with one `DECISIONS: [{id, answer}]` line. [Why](../development/wiki/plugins/taskflow/design/decide.md).
- `assets/skills/spec-task/` — inline internal skill, SKILL.md plus its usage ref `workflows/spec.md`: build-task's step 3. Contract `[--headless] [--size=S|M|L|XL] <absolute input path>`; output `spec-<slug>.md` beside the input `draft-<slug>.md`; size from `--size` or `mcp__taskflow__size-task` (own reasoning as fallback). It runs `build-task-spec`, routes `user_input_required` (`conflict`, `rounds_exhausted`) through `decide`, and resumes with every decision so far in `USER_INPUT`. At `L`/`XL` it runs an intent acceptance on the spec. Headless: at most 3 resumes. Last line `RESULT: {json}` (`path`, `size`, `reviewed`, `findings`) or a `spec-task:` stop line. [Why](../development/wiki/plugins/taskflow/design/spec-and-plan-skills.md).
- `assets/skills/plan-task/` — inline internal skill, SKILL.md plus its usage ref `workflows/plan.md`: build-task's step 4.1. Same contract and loop as `spec-task`, over `build-task-plan` (`spec-<slug>.md` → `plan-<slug>.md`). It probes graphmind and jev-api itself. Last line `RESULT: {json}` (`path`, `size`, `model`, `findings`) or a `plan-task:` stop line. [Why](../development/wiki/plugins/taskflow/design/spec-and-plan-skills.md).
- `assets/agents/*.md` — 11 static role prompts dispatched via `agentType: 'taskflow:<name>'` (`decider`: via the Agent tool's `subagent_type: "taskflow:decider"`). INTERNAL: each agent's frontmatter `description` is exactly `INTERNAL ONLY` so the model never selects one by description; callers always name them explicitly via `agentType` or `subagent_type`. Each has one caller: its build-task script, or the decide skill for `decider`; the `designer` has two: the design script and design-task's direct dispatch (`subagent_type: "taskflow:designer"`).
- `src/bin/ship-ensure-mergeable.ts` (built to `plugin/bin/ship-ensure-mergeable.mjs`, shebang plus mode 0755) — Ship merge-state remediation: `shipper` runs it before the ci-monitor loop to auto-update a `behind` branch or auto-resolve `-X ours`-clean conflicts so CI actually starts. Zero-dep Node, built from `src/bin/ship-ensure-mergeable.ts`; never force-push, never checkout --ours/--theirs. Its contract (args, env, exit codes 0/1/64, stderr texts, the one `mergeState=` line, jq's `//` quirks) is that of the 2.2.0 bash script: [migration.md](../development/wiki/plugins/taskflow/notes/migration.md).

## Constraints

- A new or renamed file under `assets/workflows/` or `assets/skills/*/workflows/` must be added to `pluginBuild.assets` in `package.json`, or the CI layout check (`development/scripts/check-plugin-layout.ts`) fails.
- The workflow scripts, agents and skill texts are shipped byte for byte from `assets/`; never edit `plugin/`.
- Pipeline files live in the session scratchpad and are written with the Write tool only, the one retry too; no Bash write path (heredoc, printf): rule `workflows.md`, [why](../development/wiki/pitfalls/worktree-and-auto-mode-sessions.md).
- The explore scribe is the `explore-scribe` agent (Read/Write only) and checks lens header/footer pairs instead of a byte count.

## Agent files and no-narration

- Every `assets/agents/*.md` starts, right after the frontmatter and title, with the verbatim "No narrative text between tool calls" paragraph. Every agent except `pr-author.md` also carries the English final-message sentence ("Write that final message in English, ..."); `pr-author` omits it (human-facing output). Copy the paragraph from an existing agent into any new one. [Why](../development/wiki/plugins/taskflow/design/workflows.md).
- Inline workflow prompts carry the same rule as a `NO_NARRATION` prefix — rule `workflows.md`.
- `design-reviewer` and `ci-monitor` carry a `tools` allowlist (Read/Grep/Glob/Bash resp. Bash, plus `ToolSearch` and the graphmind resp. jev-api tools their hints use), `designer`, `planner` (Read/Write/Grep/Glob, `ToolSearch`, graphmind tools; the planner also `mcp__jev-api__request`) and `pr-author` (Read/Write/Grep/Glob/Bash for `git log`) carry one too, `explore-scribe` and `spec-writer` one of Read and Write only, `decider` one of Read, Grep and Glob (read-only by instruction). Every agent that writes a pipeline file has no Bash unless it needs it; the other agents inherit all tools. The read-only intent of `design-reviewer` and `ci-monitor` is still an instruction in the agent body (Bash can write).

## userConfig

No `userConfig`: `claudePlugin` in `package.json` is `{}`, deliberately. Neither skill ever runs from a hook or other unattended trigger, so there is no automatic behavior for a toggle to suppress.

- `build-task` runs only on invocation (user, or the model choosing it); `dispatch-task` is `disable-model-invocation: true`, so only an explicit user invocation starts it.
- `dispatch-task` launches an unattended session once invoked, but the invocation itself is never automatic.

## Generated pipeline artifacts are always English

- Covered: the pipeline files `explore-<slug>.md`, `draft-<slug>.md`, `spec-<slug>.md`, `plan-<slug>.md`, `implement-<slug>.json` and `review-<slug>.json` (written by the skill itself in step 4.3), plus every agent's final report/structured output — always English, regardless of `$task_description`'s language.
- Enforced by the final-message rule ("Write that final message in English, whatever the language of the task or its inputs; commit messages are not covered."): `NO_NARRATION` in every workflow script, and the opening paragraph of every `assets/agents/*.md` except `pr-author.md`. Plus the explicit English instructions in `agents/designer.md`, `agents/planner.md` and `agents/spec-writer.md` plus its prompt in `assets/workflows/build-task-spec.workflow.js`. The explore file holds only the explorer and memory-recall reports (no raw task text); the explore scribe (`assets/workflows/build-task-design.workflow.js`) adds no prose of its own; the lens header/footer lines come from the script.
- Not covered (human-facing, keep the repo/user language): `pr-body-<slug>.md` and the PR/MR title (`agents/pr-author.md` "Match the repo's documentation language"), commit messages, and the final human-facing report (`SKILL.md` step 5). Code and code comments written into the user's repo are not covered either.

## Resuming inside an existing worktree/PR

- `build-task` step 1 (without `--skip-branch-check`) creates a `feature/<slug>` worktree under `.claude/worktrees/<slug>` via `EnterWorktree` `name` plus `git branch -m` (never `git worktree add` + `path`: `ExitWorktree` cannot remove such a worktree) only when the current branch IS the base branch; otherwise it stays on the current branch, including an already-checked-out worktree with an open PR/MR.
- Ship's create-or-update (`agents/shipper.md`, via `gh pr view <branch>`) then updates that PR/MR instead of opening a new one.
- `agents/worktree-merger.md` checks "is the merge-target branch checked out here" (`git branch --show-current`), never "is this the primary repo root, not a worktree" — the latter would silently merge into the wrong branch in this case.
- A non-isolated `agent()`/Agent-tool dispatch from a worktree-isolated session resolves `pwd` and `git rev-parse --show-toplevel` to that worktree, so no checkout-path threading is needed. The bridge/remote-control cwd-defaults-to-primary-root behavior is a different path; do not conflate the two.
