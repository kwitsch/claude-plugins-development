# Rule: `development/wiki/plugins/<plugin>/` (task lists and evaluations for agent sessions)

Pattern from `development/wiki/plugins/dprint/` (analysis findings worked off as tasks). Not shipped, not user documentation, English.

- Layout of every section (`wiki-check.ts` rejects other files): `index.md`; `TASKS.md` and `tasks/<id>-<slug>.md` (only with a task list); `evaluations/EVALUATION-<YYYY-MM-DD>[-<topic>].md` (topic lower case, hyphens allowed, e.g. `-f01`, `-v0.16.1`); `design/<name>.md` (reasons, measurements, residuals of one area; model: universal-lint); `notes/<name>.md` (any other page: calibration records, verification logs). File names are lower case except `EVALUATION-` and `TASKS`.
- Every plugin has a section `development/wiki/plugins/<plugin>/` with its own `index.md` (`# <plugin> knowledge`, one sentence, then `## Pages` listing `CLAUDE.md` and every page of the section except `tasks/*`; a plugin with a task list also has `## How to work a task` holding only the link to `plugins/how-to-work-a-task.md` (the one text for all plugins; plugin-specific steps go under `## Task conventions`); further plugin-specific sections after those) and an entry `[<plugin>](<plugin>/index.md)` in `plugins/index.md`. A new plugin gets both when it is scaffolded. `wiki-check.ts` enforces it.
- `TASKS.md` (same shape in every plugin): `# <plugin> tasks`, a short header (source of the findings, links to evaluations), then exactly the sections `## Remaining` (status `open`, `partial`, `docs-only`, `measurement-only`; checkbox `[ ]`), `## Done` (`done`) and `## Closed without code` (`closed`), both with `[x]`; an empty section says `None.`. Entries sorted by id, one line `- [ ] [F23](tasks/F23-slug.md) <status> <priority>: <title>` with the status in backticks (status and priority repeat the frontmatter, the title is its `title`). Optional `## Notes` and `## Dependencies` last. The entry moves section, checkbox and tag whenever the task's `status` changes. `wiki-check.ts` compares `TASKS.md` with the `tasks/` frontmatter.
- `tasks/<id>-<slug>.md` holds one task. Frontmatter: `id`, `title`, `status` (`done|partial|docs-only|open|closed|measurement-only`), `priority` (`high|medium|low|none`), `area`. Sections (`## Status`, `## Problem` and `## Related` are required): Status, Problem, Evidence, Code locations, Approach, Verification, Constraints, Related. No `# Heading` in the body: the frontmatter `title` already counts as the H1 (markdownlint MD025 on every file otherwise).
- Check every open task against the **current** code before working it: docs drift (moved files, renamed symbols, a manifest file that no longer exists, rules that moved). Obsolete or "do not do" tasks get `status: closed` with the reason, not silent deletion. Keep the old paragraph under "Earlier state:" when a task is finished.
- Update status, the section of `TASKS.md` and the evaluation together in the commit that ships the work; every finished task carries the test that proves it and the version that shipped it.
- Evaluations are dated documents with the sections `## Method`, `## Results`, `## Bug hunt` and `## Live validation` (any more after them; `wiki-check.ts` requires these four): method, one-machine numbers (median/p90, 5+ repetitions where cheap, built output, real tool versions), comparison with the earlier figures, remaining findings, a "Bug hunt" and a "Live validation" section stating exactly what was and was not run. Re-run after large changes; do not edit old numbers.
- A decision that needs the user is made by a read-only decision agent (opus, high) when the user is unavailable, and the reasoning goes into the task document.
