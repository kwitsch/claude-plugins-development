# dispatch-task: why it is built this way (do not "fix" without reading this)

The reasons behind the rule [dispatch-task.md](../../../../../taskflow/.claude/rules/dispatch-task.md). Carried over unchanged from kwitsch/claude-plugins (`plugins/taskflow/skills/dispatch-task/CLAUDE.md` at `1404384`) when taskflow moved here on 2026-11-24.

- Fork, not a call: the skill is a deliberate fork of `coding-toolbox:dispatch-agent`, so taskflow gains no cross-plugin dependency and keeps working without that plugin. Neither copy inherits the other's future fixes; that cost is accepted and permanent.
- `disable-model-invocation: true`: the skill launches an unattended `--permission-mode auto` session, so only an explicit user invocation may start one (the "explicit reason" carve-out of the skill-invocation rule in kwitsch/claude-plugins).
- Bare `Bash` in `allowed-tools`: step 1 is a compound script (`set -e`, a `name="…-$(date +%s)-$RANDOM"` assignment, `[[ "$name" =~ … ]]`, then `claude … --bg`). The Bash permission matcher requires every sub-command to be covered independently, so a narrow `Bash(claude:*)` never auto-approved the dispatch and it stalled with nobody present. Task-text safety comes from the single-quoted heredoc, not the matcher, so widening adds no exposure.
- No `git` in the skill's own Bash: `claude --worktree` starts a clean tree, which already satisfies `build-task`'s clean-`git status` precondition; the `git checkout -b` runs in the dispatched session.
- Fixed heredoc delimiter `DISPATCH_TASK_PROMPT_EOF`: the earlier per-invocation "fresh delimiter" made the model write an invented token identically twice; any mismatch left the heredoc unterminated, so the command substitution broke and the job failed to start or launched with a mangled or empty prompt. The residual risk (a task line exactly equal to the delimiter) is vanishingly unlikely and the same one `coding-toolbox:dispatch-agent` accepts; the single-quoted heredoc already blocks shell expansion. No temp file, so a dispatch failing under `set -e` leaves nothing on disk.
- Worktree base: `claude --worktree`, `EnterWorktree` and subagent `isolation: worktree` all follow the project's `worktree.baseRef` (`"fresh"` = `origin/<default branch>`, `"head"` = the local `HEAD` including unpushed commits), so the docs describe the conditional instead of assuming one.
- Branch cut: the worktree is on an auto-generated branch name, never the base branch by name, so the payload cuts `feature/<same-slug>` first; `BRANCH_NAME` is then already the pretty name that `build-task` trusts verbatim.
- `--skip-branch-check`: the state is correct by construction (a clean worktree plus the payload's own `git checkout -b`). Under `--permission-mode auto` with nobody present, a redundant check risks a conflicting decision — a stop-and-report on a tree it misreads, or a second worktree over dispatch-task's — with no one to intervene. No failure transcript backs the flag; it is a designed-against risk.
- Unattended checkpoints: `build-task` funnels every human decision through `AskUserQuestion`, so a dispatched run may pause with nobody present; the report says so instead of nudging the dispatched session toward autonomy.
