# File detection: FileChanged + watch list (do not "fix" without reading this)

- **Scope (`scopedTarget`, port of dprint's `realish`/`inScope`), shared by every event** (PostToolUse through `resolveLintTarget`, the skill driver through it, FileChanged, the watch list): the path resolved against the payload `cwd` (never `process.cwd()`) must exist, have a lintable extension (`EXT_MAP` or `TYPE_CHECK_EXTS`), its real path must lie strictly inside realpath(cwd), not be excluded, not lie inside realpath(`scratchpad_dir`) when the payload has one, and not be a dangling link. The lint keeps the lexical path; the real path is the digest key. A Write/Edit through a symlink pointing outside the cwd, or into a scratchpad inside it, is not linted.
- **Watch list** (`watchList`, SessionStart/CwdChanged): `git ls-files -co --exclude-standard -z` (tracked + untracked-not-ignored) in the cwd (`new_cwd` for CwdChanged), filtered through `scopedTarget` with a per-call directory realpath memo (`roots.dirs`, F12: one `lstat` per lintable entry plus one JS `realish` per distinct directory; scope semantics unchanged). The directory memo holds for one `watchList` call, so a directory replaced by a symlink during the scan keeps its earlier real path for the files after it (today each file re-resolves). Harmless: `watchPaths` is only the subscription list; every FileChanged re-runs `scopedTarget` without the memo before linting. The scan stops at the first file that makes more than `WATCH_LIMIT` (5000) distinct lintable in-scope files: nothing is watched and stderr gets a "more than 5000 files" note (no exact count; the rest of the list is not scoped, `git ls-files` itself still runs to completion); a git failure (not a repo, no git, timeout) watches nothing.
- **FileChanged skip order** (`fileChangedHandler`, first match wins, every skip = `{}`): `unlink` event; out of scope; content equals the digest Write/Edit recorded; `git --no-optional-locks --literal-pathspecs status --porcelain --untracked-files=normal --ignored=matching -- <real>` (cwd `dirname(real)`) prints nothing (tracked, unchanged) or starts with `!!` (ignored). A git failure lints. `add` and `change` are handled alike. Then the slot gate (below).
- **Slot cap (F10, 0.15.9):** after the git gate, `fileChangedHandler` takes one of K = `FILE_CHANGED_SLOTS` = `max(2, floor(os.availableParallelism() / 4))` slots (3 on 12 cores) through `acquireSlot`: slot files `${CLAUDE_PLUGIN_DATA || os.tmpdir()}/fc-slots/<i>`, claimed by `writeFileSync(slot, pid, { flag: "wx" })` (an exclusive create, not temp file + `renameSync`: the claim must fail when held). A slot is stale (`slotStale`, removed before the claim) when its pid is dead (`process.kill(pid, 0)` throws ESRCH) or its mtime is at least 90 s (`HOOK_TIMEOUT_MS`) old or at least 90 s in the future (the future side has a tolerance because a fresh slot's sub-ms mtime can be ahead of integer `Date.now()`); EPERM and an empty or unparsable pid count as held until the mtime rule. While all K are held it polls every 100 ms (`Atomics.wait`) until process uptime reaches `FILE_CHANGED_BUDGET_MS` (85 s) minus the file's lint reservation (`hook-design.md` "Timeout budget", git); one full round over the slots always runs first. No slot in time: `{}` plus the stderr note `universal-lint: FileChanged: no lint slot free in time, <path> not linted`, exit 0 (never rewakes). Any other slot error (mkdir, create, stale removal) lints without a slot (fail open, as before F10). Release: `rmSync` in a `finally` around `lintResolved`, inside its own `try` so a failed release never discards findings. FileChanged only: PostToolUse Write/Edit and the skill driver take no slot and never wait (no-debounce user decision 2026-11-06).
  - Residuals:
    - the stale-reclaim race may briefly allow K+1 lints
    - a wall-clock jump of 90 s or more makes live slots look stale
    - a reused pid holds a dead slot until the 90 s mtime rule
    - no FIFO among waiters
    - the cap counts lints, not the waiting hook node processes nor their `git status` children (each waiting hook's git gate runs before the slot gate, so git children are not bounded by K)
    - since F18 a `.ts/.tsx/.mts/.cts` lint without an oxlint `typeCheck` config runs its chain tool and `tsc` at once, so up to 2K heavy children run per burst (a CPU-starved `tsc` that hits `TSC_SPAWN_TIMEOUT_MS` skips, fail open)
    - a slot per child was not chosen because it would halve the lint throughput of the common oxlint-`typeCheck` case, which runs one child
    - a timed-out check's whole process group is killed (SIGTERM, SIGKILL after 1 s; F18) and a holder killed with SIGTERM/SIGINT/SIGHUP kills its live groups first, but a holder SIGKILLed by the 90 s backstop leaves its detached children to finish on their own
    - every session using the same data dir shares the K slots, and the tmpdir fallback shares them across users (another user's slot dir makes lints fail open)
    - a data dir shared across pid namespaces (e.g. a container and its host) makes a live holder's pid look dead (`process.kill` ESRCH), so its slot is reclaimed and K+1 lints run
    - a file `lintResolved` would not lint anyway (no eslint/oxlint/stylelint config, no tool found) still takes or waits for a slot and can get the give-up note
- **Project-check lock (F13, 0.15.12):** FileChanged only (`coalesce` from `hookEventName` in `lintResolved`). `coalesceProjectCheck` wraps the `tsc`/`go vet`/`golangci-lint`/`cargo` spawn: `fc-locks/<key>.lock` (`wx` + pid, `slotStale`; shared by all sessions, so their runs serialise) and `<key>-<hashPath(session_id)>.last` (`Date.now()` before the spawn, written after a run without error/signal; per session: two sessions watching one file each get the findings); key = `hashPath(tool:tsconfig|package dir|Cargo.toml)`. Skip when `ctime(file) < .last <= Date.now()`, checked every 100 ms while waiting and once after the claim. Taken after the slot (held while waiting); at uptime `FILE_CHANGED_BUDGET_MS` − spawn timeout, or on any error, it runs unlocked.
  - Residuals:
    - drvfs/9P clock skew covers too early (lost finding) or late (extra run)
    - coarse ctime tick vs `Date.now()`
    - a holder killed after `.last` loses the report
    - the report targets the tsconfig dir/package/crate
    - slot-cap stale-reclaim/data-dir/pid-namespace residuals
- **Digest store:** PostToolUse records the SHA-256 (base64) of the content the tool wrote (`writtenContent`: Write's `tool_input.content`, or the Edit's `structuredPatch` applied to its `originalFile`), never of the disk, at `${CLAUDE_PLUGIN_DATA || os.tmpdir()}/written/<hashPath(real path)>` (temp file + `renameSync`, one file per real path, no locking) before it lints. Not the disk: a parallel formatter hook's or an editor's write would otherwise skip its FileChanged, and the Edit's range gate drops findings outside the edit. Without content (missing field, a patch that does not fit) the old digest is removed. A missing digest is no match; a write error is swallowed (cost: one duplicate lint). Cost of the content digest: a CRLF file (Edit's `originalFile` is the LF view) and every formatter rewrite get one FileChanged lint more, never one less. The skill driver records nothing. No pruning (bounded by the number of files ever written). Race: a FileChanged delivered before the digest lands lints twice (duplicate findings, never lost ones); measured 0 of 55 echoes missed, race margin p50 600 ms (F32). Hashing is unbounded by file size by design (about 11 ms per 10 MB, 250 MB RSS at 200 MB; F25 closed docs-only): a size skip would make FileChanged lint the file, and a lint skip is a policy change (F19).
- **FileChanged lints the whole file:** no edit-range gate (`ranges = null`).
- **Static watch list (dprint F24, F15):** files created after SessionStart/CwdChanged are not watched until the next SessionStart/CwdChanged. A watched file replaced by unlink+create (checkout, restore) keeps its watch unless Claude Code reported it as `unlink` (2.1.319, flat 50-file repo: 1 and 3 of 50 in two runs; table in F15). Re-emitting the list from FileChanged cannot re-arm them: `watchPaths` on FileChanged stdout is honoured under `asyncRewake`, but the watcher is re-created only when the sorted list changes, and a changing list drops events during the checkout (F15, docs-only). Refreshing after Bash commands is a follow-up.

## Path exclusions (`isExcludedPath`)

- Skips `node_modules/`, `vendor/`, `.git/`, plus two Claude-Code-owned subtrees that can land inside a broad `cwd` (e.g. `$HOME`, or a repo root nesting worktrees): `.claude/worktrees/` (harness-created git worktrees, never this session's own content) and `.claude/agent-memory/` (gitignored agent runtime artifacts).
- Any basename containing `.local.` (e.g. `settings.local.json`) is skipped in any directory, matching `.claude/.gitignore`'s `*.local.*` personal-override convention.
- **Deliberately narrow — not a blanket `.claude/` exclusion.** Tracked content under `.claude/` (`rules/`, `agents/`, `skills/`, `settings.json`) must keep getting linted; a `.claude/rules/*.md` edit still triggers markdownlint.
- Exclusion is checked on the path relative to the **real** cwd (inside `scopedTarget`), so a symlinked cwd or file cannot dodge it.
