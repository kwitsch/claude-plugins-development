# File detection: FileChanged + watch list (do not "fix" without reading this)

- **Scope (`scopedTarget`, port of dprint's `realish`/`inScope`), shared by every event** (Write/Edit through `resolveLintTarget`, the skill driver through it, FileChanged, the watch list): the path resolved against the cwd of the call (never `process.cwd()`) must exist, have a lintable extension (`EXT_MAP` or `TYPE_CHECK_EXTS`), its real path must lie strictly inside realpath(cwd), not be excluded, not lie inside realpath(`scratchpad_dir`) when the call has one, and not be a dangling link. The lint keeps the lexical path; the real path is the digest key. A Write/Edit through a symlink pointing outside the cwd, or into a scratchpad inside it, is not linted.
- **Worktree scope base (0.18.0, U1, P6):** the cwd of a Write/Edit is `$.session.cwd()` read per edit in the mod's `tool.call`, per calling agent: the main conversation after EnterWorktree is `<root>/.claude/worktrees/<name>`, a worktree-isolated subagent its own `<root>/.claude/worktrees/agent-<id>`, a non-isolated subagent the main conversation's current directory. It is never the project root by default and never derived from the file path, so a session working in a worktree gets its edits linted (`.claude/worktrees/` is excluded only relative to the real cwd, and the cwd is the worktree). The unknown-scratchpad rule of a keyed call: no scratchpad exclusion, the cwd rule still applies. Evidence and cases: [evaluation](../evaluations/EVALUATION-2026-11-26-mod-server.md), "Third probe round", P6; [hook-design.md](hook-design.md) "Scope base and cwd".
- **Watch list** (`watchList`, SessionStart/CwdChanged, the command hook `src/hooks/watch-paths.ts`): `git ls-files -co --exclude-standard -z` (tracked + untracked-not-ignored) in the cwd (`new_cwd` for CwdChanged), filtered through `scopedTarget` with a per-call directory realpath memo (`roots.dirs`, F12: one `lstat` per lintable entry plus one JS `realish` per distinct directory; scope semantics unchanged). The directory memo holds for one `watchList` call, so a directory replaced by a symlink during the scan keeps its earlier real path for the files after it (today each file re-resolves). Harmless: `watchPaths` is only the subscription list; every FileChanged re-runs `scopedTarget` without the memo before linting. The scan stops at the first file that makes more than `WATCH_LIMIT` (5000) distinct lintable in-scope files: nothing is watched and stderr gets a "more than 5000 files" note (no exact count; the rest of the list is not scoped, `git ls-files` itself still runs to completion); a git failure (not a repo, no git, timeout) watches nothing. The watch list is the only command hook left: an `mcp_tool` CwdChanged hook never fires (live 2.1.332, P6), and watch paths come only from a command hook (fact 3c).
- **FileChanged skip order** (`file_changed` tool of the server, `fileChangedHandler`, first match wins, every skip = `{}`): `unlink` event; out of scope; content equals the digest Write/Edit recorded; then the git gate. Lock wait (F41, 0.19.0): while `<gitdir>/index.lock` exists (`gitDirOf`: the first `.git` above the file's real directory, a directory or the `gitdir:` file of a linked worktree or submodule, not cached) the call polls every 100 ms (async `sleep`, no `admitGit` permit held; a cancelled call returns and keeps its record) up to one `GIT_TIMEOUT_MS` (10 s) deadline it shares with the `git status` after it. Then `git --no-optional-locks --literal-pathspecs status --porcelain --untracked-files=normal --ignored=matching -- <real>` (cwd `dirname(real)`, timeout = what is left of that deadline, at least 1 ms) skips when it prints nothing (tracked, unchanged) or starts with `!!` (ignored), or, while `MERGE_HEAD`, `rebase-merge` or `rebase-apply` exists in the git dir, when its XY is unmerged (`DD AU UD UA DU AA UU`) or staged-only (X in `MADRC`, Y a space). Every git skip deletes the FileChanged record this call just journaled (`journal.delete(rec.name)`), so the Stop/SubagentStop sweep, which lints every pending record whole without a git gate, does not lint the file either. A git failure or timeout lints; no git dir found means no lock wait and no merge-state check (fail open). `add` and `change` are handled alike. The git gate is async (it never blocks the server). Then the slot gate (below).
  - Why (F41): a file that `git pull` or a branch switch rewrote was linted: its record stayed after the clean verdict and the sweep linted it at the next Stop (read in code), and an event that arrived while git was still writing (git writes the worktree under `index.lock`, then commits the index, then moves HEAD) saw `M` against the old index and linted inline (reasoned from git's write order, not reproduced live). The record deletion closes the first, the lock wait the second. Task: [F41](../tasks/F41-skip-git-operation-changes.md).
  - Every cause (user decision q1, 2026-11-28): a clean or ignored verdict skips and deletes the record whatever caused it: pull, branch switch, `git checkout -- f`, `git restore`, `reset --hard`, `stash`, an editor writing back committed bytes. Committed content was already "not ours" for the inline gate; the sweep was the inconsistency. Rejected: reflog attribution and a Bash `tool.call` matcher (F41).
  - Stopped merge or rebase: conflicted and auto-merged files are git's content, from `git pull` or a manual `git merge`/`git rebase` alike (not told apart; parsing `MERGE_MSG` rejected as fragile). An outside edit during the merge shows ` M`, `MM` or `??` and lints.
  - Worktree switch: EnterWorktree, ExitWorktree and `git worktree add` rewrite no file of the start directory, and the watch list stays on it (R12, below), so they cause no FileChanged lint and need no code. A pull or switch inside a linked worktree goes through the same gate (`gitDirOf` follows the `gitdir:` file).
  - Residuals:
    - only the call's own record is deleted: pending Write/Edit records of the agent for a file git later rewrote still make the sweep lint it
    - between git's index commit and its HEAD update (microseconds) status shows staged `M ` without merge state: that file lints
    - `pull --autostash`, `switch -m`, `checkout -m`, cherry-pick, revert and autostash conflicts leave dirty files (` M`, `MM`) that lint (fail open)
    - a stale `index.lock` (crashed git) makes each event wait the full 10 s; `git status` then gets 1 ms, times out and the file lints (fail open); a long unrelated git command holding the lock (`git add` of a large tree) delays events the same way, inside the budget (`hook-design.md` "git")
    - `GIT_DIR`/`GIT_WORK_TREE` set in the server's environment can make `gitDirOf` name the wrong dir: that only shortens or skips the lock wait and the merge-state check, the status gate still decides
- **Slot cap (F10, 0.15.9; in memory since 0.18.0):** after the git gate, `fileChangedHandler` takes one of K = `FILE_CHANGED_SLOTS` = `max(2, floor(os.availableParallelism() / 4))` slots (3 on 12 cores) through `acquireSlot`: an in-process FIFO semaphore, one per server, so one per session. A lint releasing a slot wakes the first waiter in arrival order. The wait ends at call time (`elapsedMs()` of the call context, `FILE_CHANGED_BUDGET_MS` 85 s) minus the file's lint reservation (`hook-design.md` "Timeout budget", git); one full round over the slots always runs first. No slot in time: `{}` plus the stderr note `universal-lint: FileChanged: no lint slot free in time, <path> not linted`, exit 0 (never rewakes). The release happens in a `finally` around `lintResolved`, so a failed release never discards findings. FileChanged only: Write/Edit and the skill driver take no slot and never wait (no-debounce user decision 2026-11-06). Earlier state (0.15.9 to 0.17.4): slot files `${CLAUDE_PLUGIN_DATA || os.tmpdir()}/fc-slots/<i>` claimed by an exclusive `wx` create holding the pid, with dead-pid, 90 s mtime and polling rules.
  - Residuals:
    - no stale-slot reclaim is needed any more: a holder that dies takes the server with it (R1 in [settle-window.md](settle-window.md))
    - since F18 a `.ts/.tsx/.mts/.cts` lint without an oxlint `typeCheck` config runs its chain tool and `tsc` at once, so up to 2K heavy children run per burst (a CPU-starved `tsc` that hits `TSC_SPAWN_TIMEOUT_MS` skips, fail open)
    - a slot per child was not chosen because it would halve the lint throughput of the common oxlint-`typeCheck` case, which runs one child
    - the cap counts lints, not the waiting calls; their `git status` spawns run before the slot gate and are admitted separately, `GIT_GATE_MAX` (8) at a time in FIFO order (`admitGit`), so a burst of events does not fork all of them at once on the one event loop
    - a timed-out check's whole process group is killed (SIGTERM, SIGKILL after 1 s; F18); a cancelled call kills its running group (`notifications/cancelled`), a server that ends (stdin EOF, SIGTERM) kills its live groups (`installSignalHandler`: the signals and an `exit` listener), and only a SIGKILLed server leaves its detached children to finish on their own
    - K is per session (R2): two sessions each get K slots and their lints do not share a slot count; the project-check lock is per session too
- **Project-check lock (F13, 0.15.12; in memory since 0.18.0):** FileChanged only (`coalesce` from the event in `lintResolved`). `coalesceProjectCheck` wraps the `tsc`/`go vet`/`golangci-lint`/`cargo` spawn: a lock per key (`hashPath(tool:tsconfig|package dir|Cargo.toml)`), held by one run at a time within the session (R2: sessions no longer serialise each other's runs) and a `.last` time per key and session (`Date.now()` before the spawn, written after a run without error/signal): two sessions watching one file each get the findings. Skip when `ctime(file) < .last <= Date.now()`, checked every 100 ms while waiting (no `await` lies between the lock test and the claim, so there is no check after it). Taken after the slot (held while waiting); at call time `FILE_CHANGED_BUDGET_MS` − spawn timeout, or on any error, it runs unlocked. Earlier state: lock and `.last` files under `${CLAUDE_PLUGIN_DATA || os.tmpdir()}/fc-locks/`, shared by all sessions.
  - Residuals:
    - a holder that crashes after `.last` loses the report (the server dies with it, R1)
    - coarse ctime tick vs `Date.now()`, and a clock skew of the file system (drvfs/9P) covers too early (lost finding) or late (extra run)
    - the report targets the tsconfig dir/package/crate
- **Digest store (in memory since 0.18.0):** a Write/Edit records the SHA-256 (base64) of the content the tool wrote (`writtenContent`: Write's `tool_input.content`, which the mod fills from the Write result's own `content`, the text that landed, because the event's `content` is the model's text before a PreToolUse rewrite such as universal-format's and its digest would make the Write's own FileChanged echo lint again, live 2.1.332; or the Edit's `structuredPatch` applied to its `originalFile`), never of the disk, in the server's `written` map (keyed by real path, `capSet` with `STATE_CAP` 5000, oldest dropped; per session) before it lints. Not the disk: a parallel formatter hook's or an editor's write would otherwise skip its FileChanged, and the Edit's range gate drops findings outside the edit. Without content (missing field, a patch that does not fit) the old digest is removed. A missing digest is no match. Cost of the content digest: a CRLF file (Edit's `originalFile` is the LF view) and every formatter rewrite get one FileChanged lint more, never one less. The skill driver records nothing. Race: a FileChanged delivered before the digest lands lints twice (duplicate findings, never lost ones); measured 0 of 55 echoes missed, race margin p50 600 ms (F32, earlier state). Dropped digests past the cap cost one duplicate lint. Hashing is unbounded by file size by design (about 11 ms per 10 MB, 250 MB RSS at 200 MB; F25 closed docs-only): a size skip would make FileChanged lint the file, and a lint skip is a policy change (F19).
  - Residual R4 (c) of [hook-design.md](hook-design.md): a keyed call with an invented session id can make one FileChanged of an existing file count as an echo for the real session when the content matches.
- **FileChanged lints the whole file:** no edit-range gate (`ranges = null`).
- **Static watch list (dprint F24, F15):** files created after SessionStart/CwdChanged are not watched until the next SessionStart/CwdChanged. A watched file replaced by unlink+create (checkout, restore) keeps its watch unless Claude Code reported it as `unlink` (2.1.319, flat 50-file repo: 1 and 3 of 50 in two runs; table in F15). Re-emitting the list from FileChanged cannot re-arm them: a changing list drops events during the checkout (F15, docs-only). Refreshing after Bash commands is a follow-up.
- **Watch list after EnterWorktree (R12):** no CwdChanged event fires after EnterWorktree (live 2.1.332, P6), so the watch list still belongs to the start directory, as in 0.17.4; only Write/Edit is covered in a worktree. Follow-up: a PostToolUse `EnterWorktree`/`ExitWorktree` hook, as dprint has (spec non-goal, not done in 0.18.0).

## Path exclusions (`isExcludedPath`)

- Skips `node_modules/`, `vendor/`, `.git/`, plus two Claude-Code-owned subtrees that can land inside a broad `cwd` (e.g. `$HOME`, or a repo root nesting worktrees): `.claude/worktrees/` (harness-created git worktrees, never this session's own content) and `.claude/agent-memory/` (gitignored agent runtime artifacts).
- Any basename containing `.local.` (e.g. `settings.local.json`) is skipped in any directory, matching `.claude/.gitignore`'s `*.local.*` personal-override convention.
- **Deliberately narrow — not a blanket `.claude/` exclusion.** Tracked content under `.claude/` (`rules/`, `agents/`, `skills/`, `settings.json`) must keep getting linted; a `.claude/rules/*.md` edit still triggers markdownlint.
- Exclusion is checked on the path relative to the **real** cwd (inside `scopedTarget`), so a symlinked cwd or file cannot dodge it. `.claude/worktrees/` is excluded relative to the real cwd: a session whose cwd is the worktree itself is not affected, because the exclusion applies below the cwd.
