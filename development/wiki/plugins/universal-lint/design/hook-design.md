# Hook design (do not "fix" without reading this)

## Surface (0.18.0, since 2026-11-26)

Decision of 2026-11-26, made by the user after the live probe of Claude Code 2.1.332 ([evaluation](../evaluations/EVALUATION-2026-11-26-mod-server.md), "Third probe round"). It reverses the 2026-11-06 decision (command hooks, no MCP server, no persistent process). Reason: a managed machine bypasses every `classic.*` hook of a user-tier mod, so the Stop sweep, SubagentStop and FileChanged need `mcp_tool` hooks, and the state they share (journal, digests, outbox, slots, probe memo) needs one process that outlives the hook calls. Rejected alternatives, as the spec condensed them: **B** Write/Edit through a PostToolUse `mcp_tool` hook with the mod only for the wake (workable, but the mod, the key and the shared `mcp-core` change stay needed, and the patch arrives as JSON text); **C** six command hooks plus a socket to the server (a second protocol and trust boundary; a command hook cannot reach a stdio server); **D** the server writes ready reports to a file that the mod polls with `$.fs` (file state and a poll; `$.fs` has no verified delete; a mod cannot see `CLAUDE_PLUGIN_DATA`); **E** the mod alone with `turn.complete` as the stop signal (it cannot block a stop; no engine event exists for FileChanged); **F** caller-discrimination variants (no discrimination, a mod-generated first-wins key, finding text in `next_report`, key rotation). Chosen: A, one server-issued key, text-free `next_report`.

- **Shape:** the mod `src/hooks/register.ts` (`plugin/hooks/register.js`) sends each Write/Edit (`tool.call` matcher `{ tool: ["Write", "Edit"] }`, after `next`, with `structuredPatch`, `originalFile` and, for a Write, `content` from `r.result`: the event's own `content` is the model's text before a PreToolUse rewrite such as universal-format's, so a digest of it would not match the disk, live 2.1.332) to the server tool `file_edited`, appends the answer's `context` to the tool result, and runs the idle wake. The server (`src/mcp/server.ts`, `serveMcp` of `@shared/mcp-core.js`, name `lint`) holds all state in memory and serves five tools: `file_edited` and `next_report` (model-visible), `stop`, `file_changed` and `prompt_submitted` (hook-only). `mcp_tool` hooks: UserPromptSubmit `prompt_submitted` (timeout 10), FileChanged `file_changed` (timeout 100), Stop and SubagentStop `stop` (timeout 100). Command hook: `src/hooks/watch-paths.ts` for SessionStart and CwdChanged only (timeout 30). Every hook carries an English `statusMessage` (`universal-lint: linting the changed file`, ...; pinned in `tests/manifest.test.ts`): the 0.17.x hooks were silent, but a Stop or FileChanged lint can run for seconds and the person should see why the turn waits.
- **Server lifetime (R1, R2):** one server process per session process; journal, digests, outbox, keys and roots live and die with it. A crash, a kill or `/reload-plugins` loses pending findings silently (R1; fail open). Two sessions have two servers, so the project-check lock and the FileChanged slot cap are per session (R2). The server is never blocking: no `Atomics.wait`, `execFileSync` or `spawnSync` on any path a tool call reaches; stdin close runs `closeAll()` (aborts the detached jobs, releases the waiters) and the server then exits at once, which kills every live linter group, also those of awaited runs (the `exit` listener of `installSignalHandler`; a client that dies sends no signal first).
- **Cancellation and the idle window (PR #148 review, 2026-11-26):** (a) `run()` aborts a call's controller with the reason `CANCELLED` on a client cancel (and when stdin closes) and with `"deadline"` at `HOOK_TIMEOUT_MS`; `callCancelled()` tells them apart. On a client cancel `lintFileHandler` and `fileChangedHandler` return without `settleClean` or a claim, `sweepHandler` puts the records of every file it claimed back into the journal (`restoreClaims`, also of files whose lint had already finished: their findings were not delivered), the sweep's lanes stop taking files and `stop` drains and blocks nothing: the next stop lints the file. A deadline keeps the old behaviour (records cleared, no retry: re-linting a hanging file for another 90 s at every stop was rejected). Only hook-called tools (`stop`, `file_changed`) and the aborting of a detached job are ever cancelled by the client; a mod's `$.mcp.call` is not cancelled when its dispatch is abandoned (P7, 2.1.325), so a finding delivered in the `context` of an abandoned `file_edited` dispatch is lost (accepted residual R13: the server cannot see the abandonment and a release-by-token protocol was judged not worth a tool). (b) The mod registers `prompt.submit` (typed and queued prompts; the mod's own `$.prompt.submit` does not pass through it, live 2.1.332 managed) and bumps its generation, and the wake loop checks the generation before every poll and after it: a prompt that arrives before the first poll or between polls ends the loop. The typed-ahead prompt's event fires before the running turn's `turn.complete`, which then arms a fresh loop, as intended.
- **Session key (U2, U8, D15):** the server issues one key per session id and process (`randomUUID`; `/clear` changes the session id inside the same server process, live 2.1.332, so a single key per process would reject the mod after `/clear`) to the first call that asks for it (the mod's `session.start` handshake, or its next call after a respawn). `file_edited` and `next_report` act only for that key. A call with a missing or wrong key gets the neutral answer at once: it consumes nothing, journals nothing, starts no lint, displaces no waiter and changes no key state. No rotation, no contested-key logic. The mod keeps one key per session id (`/clear` and an in-process `/resume` raise no `session.start`, and `/resume` can return to an id the server keyed before) and overlapping first calls of a session wait for the one that fetches the key: the server answers every other call without the key neutrally, which the mod reads as "nothing to report", so a lint would be lost silently. The bar is accident-proof, not adversary-proof: a model that wants to misbehave has Bash and Read on the project anyway.
- **Accepted residuals of the key (R4):** (a) a non-adversarial caller is assumed; (b) a stray call that is the first call for a session against a freshly respawned server takes the key, and that session's edits stay unlinted until the server process is replaced (nothing heals it short of a restart: rotation is dropped); (c) a caller that invents a session id gets a key for it and can have a lintable file in any existing directory linted read-only with the findings returned to itself (it could read the same file with Read), and can make one FileChanged of that file count as an echo for the real session; it cannot reach the real session's outbox, journal or waiter; (d) a report can be one edit stale when it rides the next `file_edited` (delivered rather than dropped: report more, never less).
- **Scope base and cwd (U1, D4):** the cwd of an edit is `$.session.cwd()` read per call in the mod's `tool.call`, never cached, never the project root by default. A keyed `file_edited` accepts a cwd when it is an absolute path to an existing directory that is not a filesystem root (`realpathSync`), memoised in `roots` and validated again after eviction. It is not confined to the project or to earlier roots: an isolated subagent's worktree need not lie inside the start directory, and its SubagentStop comes after its edits, so a stricter rule would journal nothing there. The key is the confinement.
- **Idle wake (U3, U6, D6, F-P5, F-P7):** the mod arms the wake poll only at the main conversation's `turn.complete` and only when it knows the session is not headless (`CLAUDE_CODE_ENTRYPOINT` not starting with `sdk`: first the mod's `$.env.get` at `session.start`, second the server's key answer; `true` or unknown means not armed; no marker file). A pending `$.mcp.call` keeps `claude -p` alive until it answers (33 s against 4 s), which is why headless runs never arm it. `$.prompt.submit` is called only while the session is idle (between the main `turn.complete` and the next UserPromptSubmit), with the one constant `WAKE_TEXT`; `prompt_submitted` drains the outbox into the woken turn's context.
- **Delivery:** see [settle-window.md](settle-window.md) "Delivery matrix". Finding text leaves the server only through the keyed `file_edited` answer, the `stop` block and the `prompt_submitted` context.
- **Shared state caps (U8, D16):** `capSet` with `STATE_CAP` (5000) for `written`, `roots`, `scratchpads`, `keys` and `outbox`: past the cap the oldest entry is dropped, a dropped digest costs one duplicate FileChanged lint, a dropped key one re-issue, a dropped scratchpad its exclusion until the next hook call, a dropped outbox text that report. `journal`, `activity`, `blocked` and `projectLast` keep their `PENDING_TTL_MS` prune (24 h) and are not capped a second time.
- **Timeout budget per tool call (replaces the per-process budget of the earlier state):** an awaited lint runs under `HOOK_TIMEOUT_MS` (90 s, above every inner `*_TIMEOUT_MS`, the same derivation as in "Timeout budget" below); a detached job under its own controller; `next_report` at most `WAKE_WAIT_MS` (25 s); the hook-level timeouts of `file_changed` and `stop` are 100 s, 10 s above the per-call deadline, so a worst-case sweep ends on its own deadline and never races the hook cancel; `prompt_submitted` 10 s. A cancelled call (`notifications/cancelled`, e.g. a hook that hit its timeout) spawns nothing new, kills the running group, and sends no answer; a sweep that already claimed records loses those findings (as a killed hook process did before).
- **Engine facts (live 2.1.332, managed; evaluation page):** F-P1 to F-P8 are filed in `development/wiki/facts/` (`mods-engine-tools.md` "`tool.call` event and result", `mods-engine-session.md` "Agent identity and cwd", `mods-engine-lifecycle.md`, `mods-engine-io.md` "`$.mcp`", `claude-code-command-hooks.md` "Payloads"). One version, one machine (R8): a later Claude Code that changes one of them is a redesign with the advisor, never a quiet degradation.
- **Model-visible tools (R4, D3):** `file_edited` and `next_report` cannot be guarded by the harness (`tool.check` reported never to run under the managed policy, 2.1.332, unverified in this repo; see [mods-engine-tools.md](../../../facts/mods-engine-tools.md)); `stop`, `file_changed` and `prompt_submitted` stay hook-only (`visibility: ["app"]`), so the model cannot forge a stop, a prompt or a file-change event. The tool descriptions say "Internal: called by the universal-lint plugin".

## Earlier state (0.14.0 to 0.17.4, superseded on 2026-11-26)

- **Six `command` hooks, one entry:** every event runs `"${CLAUDE_PLUGIN_ROOT}/hooks/lint-file.mjs"` (the placeholder is quoted so a plugin path with a space survives; `claude plugin validate` warns otherwise); `main()` dispatches on `hook_event_name`. No hooks.json `async` flag (the hook itself has an async `main` since 0.15.4, see the stdin sub-bullet), no `statusMessage` (silent), no matcher on the five non-tool events. No `if` or FileChanged matcher filter (F26, Claude Code 2.1.321): `if` takes one rule per handler (46 handlers to keep in step with `EXT_MAP`) and a FileChanged matcher also registers watch entries, matches case-sensitively and cannot skip the hook's own echoes or `unlink`; the saving is ~40 ms background CPU per spawn.
  - PostToolUse `Write|Edit` (`PostToolUse[0]`, index pinned by `tests/manifest.test.ts`): `timeout: 90`, `asyncRewake: true`. Records the content digest (see `file-detection.md`), then lints; a subagent's edit (`agent_id` in the payload) is only journaled (`settle-window.md`). A payload without `hook_event_name` is treated as PostToolUse.
  - Stop and SubagentStop (F40, 0.17.0): `timeout: 90`, synchronous (no `asyncRewake`: exit `2` must reach the stopping agent, which then continues). Lint the files whose edits by that agent no report has covered yet (`sweepHandler`, `settle-window.md` "Sweep"); nothing pending costs one process start and one `readdir`.
  - SessionStart and CwdChanged: `timeout: 30`. Print the watch list on stdout as `{"hookSpecificOutput":{"hookEventName":<event>,"watchPaths":[…]}}`, only when it is non-empty; always exit `0`. CwdChanged builds the list for `new_cwd`; empty output leaves Claude Code with an empty watch list.
  - FileChanged: `timeout: 90`, `asyncRewake: true`. Lints a watched file changed outside Write/Edit with the same findings contract; the text is prefixed `universal-lint (changed outside Write/Edit): ` and `hookEventName` is `FileChanged`.
  - `asyncRewake` runs the hook in the background like `async`, but exit `2` wakes Claude with stderr as soon as the lint finishes, instead of the findings waiting for the next turn. Contract: findings = the `universal-lint…: …` text on stderr + exit `2`; nothing to report = no output, exit `0`.
  - stdin: `main` reads the payload with `await json(process.stdin)` (`node:stream/consumers`), never a synchronous `readFileSync` on fd 0. The `node:process` import (and any `process.stdin` access) opens fd 0 as a non-blocking pipe handle, so a sync read throws EAGAIN whenever the writer is late or the payload exceeds the pipe buffer (about 128-192 KB; Edit payloads carry the whole `tool_response.originalFile`, Write payloads the whole `tool_input.content`), and the fail-open catch made that a silent skip: no lint, no digest (F05, fixed in 0.15.4). A read error or invalid JSON still fails open (no output, exit 0).
  - One process per event, no persistent process. `node:crypto` loads lazily (`process.getBuiltinModule`, else `createRequire` on Node < 22.3 / 20.16; floor stays 18.14), about 7 ms off every spawn that never hashes (F26).
  - No debounce of the lint: every Write/Edit lints right away in its own process (user decision 2026-11-06, removed together with the edit coalescing it required). Since 0.16.0 only the _report_ of findings is held, since 0.17.0 until the editing agent has been quiet for 20 s, and a subagent's edits are linted once at its `SubagentStop` instead (`settle-window.md`; user decision 2026-11-15). F13 (0.15.12) is, next to F10, the one FileChanged-only exception: a whole-project check is skipped when a completed one started after the file changed (dedup, not a debounce: the first event runs immediately, nothing waits for more events).
- **Command hooks, no MCP server (user decision 2026-11-06; reversed 2026-11-26, see "Surface")** (kwitsch/claude-plugins prefers a persistent MCP stdio server for hooks, as `dprint` does here):
  - Background lints (`asyncRewake`) remove the one argument for a server (per-event spawn latency): the agentic loop doesn't wait either way. The watch-list hooks are short `git ls-files` calls.
  - Safe because linting never mutates the file: findings arriving after the edit (rewake) cost no correctness. `universal-format` stays synchronous for the opposite reason.
  - Cost: no in-process state. The Write/Edit → FileChanged digest goes through disk (`CLAUDE_PLUGIN_DATA/written/`), the FileChanged concurrency cap uses slot files (`CLAUDE_PLUGIN_DATA/fc-slots/`, see `file-detection.md`), and `onPath` answers persist in `CLAUDE_PLUGIN_DATA/probe-<hashPath(PATH)>.json` (see `npx-and-local-bin.md` "PATH probe cache").
- **No launcher script, no `.mcp.json`:** a direct `.mjs` command hook needs neither; the script always runs under `node`, never `bun`.

## Timeout budget (re-derive when `hooks.json` `timeout` or any `*_TIMEOUT_MS` changes)

- Lint phases: the language's chain tool (`SPAWN_TIMEOUT_MS` 30 s; `CARGO_SPAWN_TIMEOUT_MS` 45 s for cargo; npx route `NPX_SPAWN_TIMEOUT_MS` 55 s) and, for `.ts`/`.tsx`/`.mts`/`.cts` only, `tsc` (`TSC_SPAWN_TIMEOUT_MS` 45 s). Since F18 (0.15.15) they run **at once** unless the file's oxlint config has `typeCheck: true`: then in sequence (`typescript-check.md`; the common case skips `tsc`; never a speculative `tsc`). Each timeout adds up to `KILL_GRACE_MS` (1 s) until the group is dead and the pipes close, and `SETTLE_GRACE_MS` (0.5 s) more only when a pipe holder outside the group keeps `close` from firing (see "Process groups"; every worst end below is then 0.5 s per phase later). The call's own deadline (`HOOK_TIMEOUT_MS`, 90 s: `run()` aborts the call, `spawnGroup` kills the group) is the backstop; the `mcp_tool` hook `timeout` (100 s) lies above it.
- **Settle hold (F34, F40):** the hold shrinks to what is left (`settle-window.md` "Hold"), so the hook-level `timeout` of 90 s is never the reason a finding is lost and the nominal worst cases below are unchanged (87 s FileChanged worst end: 2 s).
- **Sweep (Stop/SubagentStop, F40):** a file's lint starts only while the call time (`elapsedMs()`, since `runInCall`) is below `slotDeadlineMs(ext)` (the FileChanged reservation: `.ts`-family 10 s, `.rs` 40 s, others 55 s), so every started lint ends inside the 90 s timeout by the FileChanged derivation below; later files stay pending.
- `tsc`'s budget is below the npx one (a stale async finding arrives too late to be useful) and above the single-file one (a whole-project check is slower).
- Nominal worst case, TS file, Write/Edit, concurrent: max(chain 30 s, `tsc` 45 s) + 1 s grace = 46 s (npx chain: 56 s). Sequential fallback (oxlint `typeCheck` config, oxlint unavailable, skip verdict or timeout): chain 30 s + `tsc` 45 s + 2 s grace = 77 s inside the 90 s lint budget; npx chain 55 + 45 + 2 = 102 s (see **Accepted**). Non-TS: one phase, 30/45/55 s + 1 s. FileChanged: see **git** below.
- **Cold npx:** the single bare `npx --yes` attempt gets `NPX_SPAWN_TIMEOUT_MS` (55 s), the npx-fallback branch's worst case.
- **Local bin:** a project-local `node_modules/.bin/<name>` runs under the chain budget (`SPAWN_TIMEOUT_MS`, 30 s) and a timeout is not retried (`npx-and-local-bin.md`), so the worst cases in this section (FileChanged 86-87 s) are unchanged; the npx-cached bin runs under `NPX_SPAWN_TIMEOUT_MS` like npx, so the npx branch's worst case is unchanged.
- **Accepted:** when combined wall time exceeds the 90 s lint budget (cold npx 55 s + `tsc` 45 s + 2 s grace = 102 s, since F18 reached only on the sequential oxlint-`typeCheck` fallback) the call is aborted at its 90 s deadline and that lint's findings are silently lost. Fail-open, never a wrong result; the next edit's `tsc` hits a warm cache. Since F10 (0.15.9) also accepted: a non-TS npm-chain FileChanged lint (`.js/.jsx/.mjs/.cjs`, `.md`, `.css/.scss`) that gets its slot after call time 35 s and runs the npx route (npx-cached bin or bare npx, both under `NPX_SPAWN_TIMEOUT_MS` 55 s) can end past 90 s; the deadline aborts it, its lint is lost silently (fail open) and its slot is released when `spawnGroup` settles (the slots live in memory: no slot files, no dead-pid reclaim).
- **git:** each git call (`git ls-files` for the watch list, `git status` for the FileChanged gate) is capped at `GIT_TIMEOUT_MS` (10 s); the server runs at most `GIT_GATE_MAX` (8) FileChanged `git status` spawns at a time (`admitGit`, FIFO): a spawn forks synchronously on the one event loop, and 1000 events at once held up every other tool call by about 2 s (measured 2026-11-27, built server, WSL2). FileChanged worst end = max(slot deadline + sequential phases, lock-wait deadline + check timeout) + 1 s grace per phase, every path <= 87 s < 90 s by construction: the slot wait (F10) stops at call time 85 s (`FILE_CHANGED_BUDGET_MS`) minus the file's lint reservation, kept as the sum chain + `tsc` although the phases overlap, because the oxlint-`typeCheck` fallback runs them in sequence (`.ts/.tsx/.mts/.cts` 85 − 75 = 10 s, `.rs` 85 − 45 = 40 s, every other lintable extension 85 − 30 = 55 s); the project-check lock wait (F13; `tsc`, go, cargo go through `coalesceProjectCheck`, under the concurrent branch overlapping the chain child) stops at call time 85 s minus the check's spawn timeout (`tsc`/cargo 40 s, go 55 s) and then runs unlocked. Worst ends: `.ts` concurrent 40 + 45 + 1 = 86 s; `.ts` fallback 10 + 30 + 1 (chain), then `tsc` at once unlocked (past its lock deadline) + 45 + 1 = 87 s; `.rs` 40 + 45 + 1 = 86 s; `.go` 55 + 30 + 1 = 86 s; git's 10 s sits inside the slot deadline: the FileChanged `index.lock` wait (F41) and its `git status` share one `GIT_TIMEOUT_MS` deadline per call, so the git phase stays at most 10 s and the arithmetic is unchanged. The cold-npx overrun above applies unchanged (a kill loses that lint silently). SessionStart/CwdChanged: git 10 s plus, per listed file until more than `WATCH_LIMIT` lintable in-scope files have been found (where the scan stops; a repo with few lintable files is still scanned in full), the extension filter (no syscall), then one `lstat` per lintable listed file plus one realpath per distinct directory (F12; a symlinked leaf takes a full realpath), inside the 30 s hook timeout.
- **stdin (the watch-list command hook; the server reads JSON-RPC lines):** read to EOF with no own cap: a writer that never closes stdin holds the process until the hook `timeout` kills it (fail open; before 0.15.4 it got an instant EAGAIN skip). Claude Code closes stdin after the payload (stdin delay at most 9 ms over 50 live events, F05).
- **Backstop and signals (F18):** linter children are detached process groups, so the signal that kills the server, hook or driver does not reach them by itself; a process killed with SIGTERM/SIGINT/SIGHUP kills its live groups first (SIGKILL, then re-raises the signal), and an `exit` listener does the same when the server ends with `process.exit(0)` at stdin EOF (no signal first: a client that died); SIGKILL leaves them to EPIPE at their next write (`tsc` runs to its natural end). Inner timeouts (all < 90 s) make the call deadline reachable only through a pipe holder outside the group (see "Process groups") or a cold npx.

## Runtime behavior (`lint_file`)

- Every guard failure, clean result, skip (crash/misconfig) or missing tool returns `{}` silently (fail open); only issues produce a truncated findings text (`lintFileHandler` returns it as `additionalContext`; in 0.17.x `main` wrote it to stderr and exited 2, since 0.18.0 the server answers it as `context` of `file_edited` or as the `stop` reason). The guard chain lives in `resolveLintTarget`/`lintFileHandler`.
- **Process groups (F18, 0.15.15):** every linter/tsc child runs through `spawnGroup` (`child_process.spawn`, `detached: true`, stdin `/dev/null` as before); timeout = SIGTERM to the group, SIGKILL after `KILL_GRACE_MS` (1 s); output capped per stream at `MAX_BUFFER_BYTES` (10 MiB; ENOBUFS kills the group, further chunks discarded); the result has spawnSync's shape (`error.code` ETIMEDOUT/ENOENT/EACCES/ENOBUFS, `signal`, `status`) and every classification is as with spawnSync; the result is taken on `close` (both pipes closed, so a killed tree is reaped before the lint continues), timers cleared only then; signal handling: "Timeout budget" (Backstop and signals). POSIX only (`process.kill(-pid)`; the hook runs through a shebang `.mjs`). Residuals: a grandchild that called `setsid` leaves the group and, holding a pipe, delays `close`; the server has no process kill behind it (the old hook process had one at its 90 s `timeout`), so `spawnGroup` settles `SETTLE_GRACE_MS` (0.5 s) after the SIGKILL of a timeout, ENOBUFS or cancel (pipes destroyed, the output so far, `signal` `SIGKILL`, `error` set; without it a lint, its FileChanged slot and its project-check lock stayed held for as long as the holder lived, and an awaited `file_edited` stayed unanswered, measured 2026-11-27), while a leader that exited normally with such a holder still waits for its timeout (accepted: no registry linter leaves a pipe-holding daemon); the pid-reuse window between the leader's reap and `close` is microseconds and needs a pid wraparound; two heavy children per lint (`file-detection.md` "Slot cap").
- Selection (`selectLintTool`): the first chain tool on `PATH` wins, else the first npm chain tool with a project-local bin, else the first npm chain tool via npx; there is no per-file style-conflict skip (a linter needn't reproduce exact output the way a formatter does). The plugin does not rewrite PATH (it would change which tools are found); on WSL the Windows-PATH cost now sits only inside child processes (`go vet`'s gccgo PATH scan, ~95 ms per run), the hook-side real-vs-/mnt gap shows no /mnt penalty (largest median difference 15 ms, real PATH faster), measured 2026-11-10 on 0.15.25 (F28 doc, Evidence).
- checkstyle gets `-c <resolved config>`.
- **Config walks (F20, 0.15.17):** walks probe through `configExists`. On a path lexically under `/mnt/` (no realpath) one memoized `readdirSync` per directory prefilters names (upper-cased first segment), hits confirmed by `existsSync`, readdir errors fall back to `existsSync`; memo per call (cleared by `runInCall`; per process only in the skill driver and the watch-list hook); the skill driver's batch sees one listing per directory. ext4 unchanged. Every walk from the file (`walkUpToCwd`, `walkToRoot`: oxlint/eslint, cli2 markdownlint, stylelint, tsconfig, checkstyle, Cargo.toml, `localBin`) climbs the lexical directory of the path the lint keeps (`file-detection.md` "Scope"), never its real path, so a file reached through a symlinked directory gets the configs above the link; only the two walks that mirror a tool searching from its process cwd start at the real spawn cwd (yamllint and classic markdownlint, `line-length-guard.md`).
- stdout+stderr are captured and **never ignored**, unlike the formatter sibling: the findings text IS the payload. `maxBuffer` is raised well above the 1 MB default for the same reason — a noisy linter's output would otherwise truncate as ENOBUFS.
- Success is **classification, not a content diff** (the file is never modified): `classifyExit` applies each tool's documented exit-code contract.
- **Exception: `checkstyle`** is classified by output (`classifyCheckstyleOutput`): its exit code counts only `error`-severity violations, and the bundled default ruleset (and many real projects) run at `warning` — exit-code classification would silently miss real findings.
- `stylelint` (CSS/SCSS) does not share the 0-clean/1-issues contract: `0` clean, `2` real lint problem, anything else (`1` fatal, `64` bad usage, `78` bad config) skip (stylelint.io CLI docs).
- `yamllint` runs without `--strict`, so warnings-only findings don't surface — consistent with `eslint` (warnings don't affect its exit code either).
- `yamllint` gets its target as `./<path relative to the spawn cwd>` (`fileArg`, hook and skill driver), never absolute: it matches `ignore`, per-rule `ignore` and `ignore-from-file` (gitwildmatch) against the path exactly as given, and an anchored pattern (`gen/*.yaml`) never matches an absolute path, so ignored files gave false findings.

## Measured cost

- **Baseline:** 0.15.29 medians and machine label in the F01 doc (`development/wiki/plugins/universal-lint/tasks/F01-measurement-baseline.md`, "Measured"); numbers are machine- and load-dependent, re-measure before judging a change.
- **Harness since 0.18.0:** `node universal-lint/scripts/perf.ts [runs]` after `pnpm --filter universal-lint build` (dev only, measures `plugin/`): one built server per PATH variant (`plugin/mcp/server.mjs`) and the watch-list hook (`plugin/hooks/watch-paths.mjs`); the Write/Edit and FileChanged rows are server tool calls timed from the request line to the answer line, the SessionStart rows and the floor spawn their process directly (the 0.17.x hook-process rows are not comparable with these). Fixtures in `os.tmpdir()`, one warm-up round plus `runs` timed rounds (default 5), real PATH and PATH minus `/mnt/` dirs; exits 1 when a run misses its expected exit status or observable, 2 on a usage, missing-build or setup/spawn error. The header lists which linters were found on PATH (the `.sh`/`.py`/`.yml` rows time the missing-tool scan when they are absent, so installing one changes those rows). The `.mts Write (this repo)` row lints this checkout's `universal-lint/scripts/perf.ts` with `cwd` = the checkout root (the digest goes to the fixture's `CLAUDE_PLUGIN_DATA`, nothing is written into the repo); it times the local-bin route only when the checkout has its own `node_modules` (`pnpm install`) and `oxlint` is not on `PATH`.
