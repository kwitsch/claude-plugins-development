# Shared source layer for plugins

Analysis and plan for moving code that several plugins copy into one build-time shared source (analysis 2026-11-19, direction chosen by the user 2026-11-19; step 1, the build mechanism, is implemented, the shared modules are not).

## Duplicates found (grep, graphmind, normalized function bodies; not a full clone-detector run)

- Path-scope invariants: `isExcludedPath` (dprint `format.ts`, universal-format `handlers.ts`, universal-lint `lint-file.ts`), `realish` (dprint, universal-lint "port of dprint's"), `outside` / `relativeIfContains`, the scratchpad test. `hook-file-safety.md` wants these in one function.
- `walkToRoot`: identical in universal-format `util.ts` and universal-lint `lint-file.ts`.
- MCP dual-era server envelope in dprint, universal-format, jev-api (`requestedVersion` identical x3, `readVersion` identical x2, `HOOK_ONLY_META`, `CACHE_HINT`, version keys, the initialize / discover / cancel / ping / `tools/list` switch). `mcp-dual-era.md` names dprint's server as the model, i.e. copy-paste is the mechanism.
- Types `HookResult`, `RequestId`, `ToolDef` (type-only).
- Dev only: `tests/manifest.test.ts` in four plugins.
- Left alone on purpose: dprint `CONFIG_NAMES` copies (pinned by `dprint-gate.test.ts`), the bodies of `lint-file.ts`, jevfort and jev-api function-hooks code and transport.
- Realistic saving: about 400-500 of roughly 2,000 duplicated lines; the gain is one source for safety rules and protocol changes.

## Constraints that shape the mechanism

- A plugin runs from a cache copy without `node_modules`: shared code must be inlined or copied into `plugin/` at build time; a runtime npm package is out.
- Function-hooks modules (`$` engine, static check) take the inlined code too: see [tsdown-plugin-build.md](tsdown-plugin-build.md) and `claude-code-hook-facts.md`.
- A shared change is a build-input change of each `@shared` consumer (`ships.sh`), but CI demands no bump for consumers the PR does not touch: bump each consumer that should ship in the same PR (since 2026-11-25, [tsdown-plugin-build.md](tsdown-plugin-build.md)).
- universal-lint's `lint-file.mjs` is a self-contained command hook started on every edit: measure the cost of an extra module before it imports shared code.

## Decision (user, 2026-11-19): build-time shared source

- `development/shared/src/*.ts`, a workspace-internal folder, not a published package. Built: a plugin source imports `@shared/<name>.js`; the build inlines that module (since 2026-11-24 the preset's `overrides.alias` in each consumer's `tsdown.config.ts`) (and, transitively, the shared modules it imports) into every output that imports it, and `tsconfig.base.json` `paths` keeps `pnpm lint` type-checking it. Build: shared modules are inlined into every output that imports them ([tsdown-plugin-build.md](tsdown-plugin-build.md)); nothing ships as `plugin/shared/`. No `pluginBuild.shared` list (changed from the first plan): a plugin ships exactly the modules its sources import.
- Rejected: copy plus drift check (duplication stays); published npm package (zero-dependency rule).

## Plan

1. Done: the mechanism above, with its tests, the `build-scripts` workspace package (`development/scripts`, so `pnpm -r test` runs them) and the rules `development/CLAUDE.md`, `lint-config.md`. History: the old build shipped what a plugin imported as `plugin/shared/*.mjs` (all nine plugins rebuilt byte-identical); the tsdown build inlines it and the old build is gone (2026-11-20).
2. Done for dprint 0.14.2 and universal-format 0.19.2: `development/shared/src/scope.ts` holds `isExcludedPath`, `hasClaudeInternal`, `outside`, `relativeIfContains`, `realish` (the `realpathSync.native` form of dprint) and `walkToRoot`; tests in the workspace package `shared-code` (`development/shared/tests/scope.test.ts`, run against `src/`, 11 tests; the five `isExcludedPath` tests of universal-format moved there, so its count went 213 to 208; the sixth case, from universal-lint's tests, was added). The scratchpad test stays in each plugin (dprint checks lexical and real path, universal-format lexical only: different on purpose). Done for universal-lint 0.17.2 (user decision 2026-11-19: in this PR): `walkToRoot`, `isExcludedPath`, `realish` and `outside` come from `@shared/scope.js`; its six `isExcludedPath` tests are gone (the shared package has all six cases; 434 to 428 tests). The one behaviour change is `realish`: native `realpathSync.native` instead of `realpathSync` (benchmark 2026-11-19, ext4, 619 tracked files of this repository: identical results for all, 16 us per call native against 32 to 36 us for the JS form; not measured on 9P). Live (2.1.328, `claude -p` in a throwaway repo): the hook ran on `a.js` (exit 2, a finding), and stayed silent (exit 0) for `node_modules/pkg/b.js` and `c.local.js`; the finding text itself was a crash of my fixture's oxlint shim, so the linter output was not exercised. Cold-start cost of one extra static import in `lint-file.mjs` (measured 2026-11-19, WSL2 ext4, Node 24, 60 interleaved runs per variant of whole `node` processes, built `lint-file.mjs` 56 KB with and without an import of the 830-byte shared `scope.mjs`): PostToolUse Write on a missing file 33.8 vs 34.1 ms median (+0.27 ms, p90 37.2 vs 37.0), SessionStart 37.5 vs 38.1 ms (+0.63 ms, p90 40.5 vs 41.5): about 1 to 2 percent of the bare hook start, inside the run-to-run noise, and a fraction of the 100 ms and more a linter spawn costs. Not measured: a plugin cache on a slow mount (one more file to resolve, a few stats at 0.7 to 2.5 ms each on 9P). So the import is no reason to keep the copies. What remains before moving it: its `realish` is the non-native `realpathSync` (switch to the native form on purpose, with a test), and `isExcludedPath` is imported by name from the built `lint-file.mjs` in `tests/registry.test.ts` (the tests would import `plugin/shared/scope.mjs` instead, as the hook-tests rule allows), plus a version bump.
3. Done for dprint and universal-format (same versions as step 2, one unreleased bump per PR): `development/shared/src/mcp-core.ts` exports `serveMcp({ name, version, tools, onClose })`, `readManifestVersion(import.meta.url)` and `ToolDef<A, R>`; the loop is the dprint one, line for line. The two `server.ts` shrink to a tool table (dprint 281 to 66 lines, universal-format 205 to 25, the loop 222 lines once); `mcp-dual-era.md` names the shared module as the model. Handler input types stay per plugin: `ToolDef<A>` defaults to `never`, so any typed handler fits and the loop passes the client's object on (the handler is the trust boundary, as before). The shared package has `@modelcontextprotocol/server` as a type-only devDependency. Regression cover: the loop's own tests in `development/shared/tests/mcp-core.test.ts` (a fixture server over stdio, 15 tests: both eras, errors, cancel, close) plus the two plugins' `mcp-server.test.ts`. Mutation check on copies of `mcp-core.ts` in the scratchpad, loaded through the fixture's `MCP_CORE` seam (nothing in the repository is mutated): 25 mutants; the first run left four alive (`server/discover` without `_meta`, a notification answered, a crash of the loop not answered, a finished call's controller left in `inflight`), each got a test, final 25 of 25 killed. A pattern that is not found counts as survived, so a changed source line cannot hide a mutant. Not done: jev-api (own timeout, app-level cancel, `http` server; envelope only, if at all).
4. Dropped (checked 2026-11-19, no code): `RequestId` and `ToolDef` moved into `mcp-core.ts` with step 3 (jev-api's own copy of `RequestId` goes with its server, if that moves). The three `HookResult` types are different on purpose: universal-format's is narrow (`hookEventName: "PreToolUse"`, `updatedInput` as the exact Write or Edit shape, no `permissionDecision`), dprint's is loose (any event name, `updatedInput` optional, also answers `{}` for post-tool events), universal-lint's is an interface for a command hook's stdout without `updatedInput`. One shared type would either weaken universal-format's guarantees or constrain the others; a type-only module for a one-line alias is not worth the import.
5. Done, differently from the plan (no helper module, no bump: only tests changed): `development/scripts/tests/plugin-manifest.test.ts` holds what four plugins had copied: the `pluginManifest` unit tests (semver, `claudePlugin` marker; from jev-api's `manifest.test.ts`, removed, and dprint's `skill.test.ts`) and one test per plugin (found by `claudePlugin` in its `package.json`, so a new plugin is covered without a test) that `plugin/.claude-plugin/plugin.json` equals `pluginManifest(package.json)`, run after a build (deleted 2026-11-24 with the manifest generator). The per-plugin tests keep only what is theirs (no `userConfig`, wiring, README). Checked by raising a version in `package.json` without a build: exactly that plugin's test fails. jevfort 382 to 381, jev-api 409 to 407, dprint 229 to 227.
6. Per step: `pnpm lint && pnpm -r build && pnpm -r test`, `claude plugin validate`, `live-verify` of each touched plugin, version bump of every consumer.

Live check (live 2.1.328, 2026-11-19, `claude -p --plugin-dir <plugin>/plugin --setting-sources project` in a throwaway git repo, one run per plugin): with the rebuilt dprint 0.14.2 and universal-format 0.19.2 the MCP servers connect through `mcp-core` (stdio, 78 and 107 ms), `format_pre` is called for a Write and an Edit, the Write is formatted (`{"b":[1,2,3],...}` to `{ "b": [1, 2, 3], "a": { "x": 22, "y": [] } }` after the Edit), the hooks answer `additionalContext`, dprint also calls `drain_notices` and `file_written`. Not exercised: cancellation in a session, a scratchpad path, a worktree path, a slow mount.

Shared code in a function-hooks module (2026-11-20): on the tsdown build any bundled file, the mod entry included, may import `@shared`, with no `plugin/shared/` copy and no entry ban; the earlier `lib.mjs` rules were removed with the old build ([tsdown-plugin-build.md](tsdown-plugin-build.md)). Risk that stays: a shared module loaded by the engine must not use engine-forbidden code (`import()`, `$`); the build does not check it.

Order of value: step 2, then 3; 4 and 5 any time.
